# Дизайн подсистемы чекпоинтов CoScientist

Статус: проект для реализации (M1 → M2). Согласован с контрактом платформы Synapse
(`SynapseNmas.md`, §6, К-8), но работает автономно уже сейчас — локальное хранилище,
текущий web UI и A2A-сервер.

Документ — результат анализа кодовой базы, установленного google-adk 2.3.0
(исходники в `.venv` как ground truth), спецификации A2A и prior art
(LangGraph checkpointer, AutoGen save_state/load_state, CrewAI persistence).
Три независимых варианта дизайна прошли адверсариальную проверку; ниже — гибрид
с исправленными фактическими ошибками.

---

## 0. Решение в одном абзаце

Чекпоинт — это **снимок сессии оркестратора ADK (события + авторитетный словарь
состояния) плюс копии дисковых хранилищ модулей плюс пины конфигурации**, упакованный
в **один zip-файл** с манифестом. Снимки создаются автоматически ADK-плагином на
границах модулей (T0–T5) — в точках покоя, когда ни один агент не в середине шага.
Восстановление — **всегда новый запуск**: новый `contextId`/`session_id`, пересборка
дерева агентов из того же профиля конфигурации, регидрация сессии через
`create_session` + цикл `append_event` + одно синтетическое residual-событие,
импорт хранилищ модулей — после чего обычный A2A `message/send` с новым `contextId`
продолжает работу естественно. Промежуточное состояние саб-агентов **не сохраняется**:
дерево фиксировано на этапе сборки, вся динамика — это данные в состоянии сессии.

## 1. Ключевые факты о системе (на которых стоит дизайн)

Проверено по коду; номера строк актуальны на коммит `0b6e4b1`.

**Как устроен A2A-контур.**
- Один фабричный метод `make_a2a_app()` ([a2a/server.py:102-138](../a2a/server.py)):
  `Runner` + `InMemorySessionService` + `InMemoryArtifactService` + плагины →
  `A2aAgentExecutor` (google-adk) → `DefaultRequestHandler` + `InMemoryTaskStore`
  (a2a-sdk) → `A2AFastAPIApplication.build()` — это обычный FastAPI, к нему можно
  монтировать свои роутеры.
- Маппинг идентификаторов (`google/adk/a2a/converters/request_converter.py:66-118`):
  **ADK `session_id` = A2A `contextId`** (дословно), `user_id = f"A2A_USER_{contextId}"`
  (без аутентификации), `app_name` = ключ из `a2a.key`. `taskId` ни на что в ADK
  не маппится. Сессия создаётся лениво при первом сообщении для contextId
  (`_prepare_session`: get-or-create). **Выбор session_id — это и есть выбор
  contextId** — на этом строится всё восстановление.
- ⚠️ `a2a-sdk==0.3.26` запинен в `requirements.txt`, но **отсутствует в
  `pyproject.toml`, `uv.lock` и в `.venv`** — A2A-контур из venv сейчас не
  импортируется. Это шаг 0 плана работ.

**Как устроено дерево агентов.**
- Дерево **фиксировано на этапе сборки**: единственное место конструирования
  `sub_agents=` — [assembly/assembler.py:281](../assembly/assembler.py). Никакой код
  не добавляет/не удаляет агентов во время запуска. «Динамика» — это данные:
  `DynamicMCPToolset` пересчитывает набор инструментов на каждый ход LLM из ключей
  состояния `filtered_tools` / `deployed_mcps`.
- В remote-режиме (`run_all`) подчинённые собираются как `RemoteA2aAgent`
  ([assembler.py:217-229](../assembly/assembler.py)) — **без `output_key`**:
  дельты `search_results`/`hypotheses`/`fedot_results` коммитятся только в сессиях
  серверов-подчинённых, а в корневую сессию оркестратора попадает возврат
  инструмента-делегации.

**Как устроен HITL.**
- `request_approval`/`request_selection` — обычные `FunctionTool`
  ([hitl/tool.py:15-38](../hitl/tool.py)), блокируются в процессе на обработчике.
  ADK-путь `input_required` через `long_running_tool_ids` не используется.
- `SessionAgent` (планировщик) **буферизует финальное событие**, не отдавая его
  ([hitl/session_agent.py:105-116](../hitl/session_agent.py)) — момент «план
  сформирован, ревью ещё не показано» не виден ни одному хуку ADK.
- `hitl_toolset` — модульный синглтон с `ConsoleHITLHandler` по умолчанию;
  обработчик подменяется в рантайме (`main.py:188`, `web/app.py:100`). На
  A2A-серверах подмена не выполняется.

**Критические факты про ADK 2.3.0 (исправляют «очевидные» ошибки).**
1. **`on_event_callback` плагина срабатывает ДО записи события в сессию**
   (`runners.py:781` и `runners.py:1382-1384`, комментарий «Run the on_event
   callbacks before persisting»). Значит, снимок, снятый внутри колбэка «как есть»,
   потеряет само триггерное событие и его `state_delta`. Захват обязан **вливать
   событие-триггер, находящееся в руках, в экспорт вручную**. История до события
   N-1 при этом гарантированно закоммичена (продюсеры блокируются на
   `_enqueue_event` → `processed.wait()`, `invocation_context.py:296-299`).
2. **Часть состояния пишется прямой мутацией мимо протокола дельт**:
   `ctx.session.state['deployed_mcps'] = ...` + `yield Event(...)` без
   `state_delta` ([custom_agents.py:33-35](../agents/custom_agents.py));
   правки плана в `SessionAgent` (`session_agent.py:103/143/176`, включая ручной
   `session.events.append`). Эти ключи не восстановимы реплеем событий и **не
   доходят до storage-копии** `InMemorySessionService` (`get_session` вернёт сессию
   без них). Следствия: (а) экспортировать состояние надо из **живой
   `invocation_context.session`**, а не через `get_session`; (б) словарь состояния
   в чекпоинте — **авторитетный**, и на восстановлении он принудительно
   доносится синтетическим residual-событием (это несущий элемент, не «защитный»).
3. Промпт LLM — чистая функция от (события сессии + состояние + инструкция),
   скрытой памяти между вызовами нет → «регидрировали историю — агент продолжил
   естественно» корректно. Пары `function_call.id`/`function_response.id`
   обязаны сохраняться дословно (требование LiteLLM-пути).

**Хранилища модулей на диске** (все пишут атомарно, tmp + `os.replace`):
`task_tracker_data.json` (дисковый близнец плана), `graph_runs/research_active.json`
(граф исследования: гипотезы, статусы, evidence), `graph_runs/<run_id>.json`
(граф выполнения для web UI), `graph_runs/knowledge_memory.json`.

**FEDOT** (`fedotmas`) — корутина в процессе, строит собственный внутренний Runner
с in-memory сессией на каждый запуск. Внешнего идентификатора нет → политика
восстановления единственно честная: **detach + перезапуск с точки T3**.

## 2. Архитектура

Новый пакет `CoScientist/checkpoints/` (рядом с этим документом):

| Модуль | Роль |
|---|---|
| `model.py` | Pydantic-модели манифеста (`schema_version`), дескрипторы содержимого |
| `store.py` | Интерфейс `CheckpointStore` (5 методов: `put_blob`, `get_blob`, `put_manifest`, `get_manifest`, `list`) + `LocalZipStore` — один zip на чекпоинт |
| `capture.py` | Сбор снимка: экспорт сессии из живого `InvocationContext` + влитое триггерное событие, копии хранилищ, пины, редактирование секретов |
| `plugin.py` | `CheckpointPlugin(BasePlugin)` — автоматические триггеры T1–T5 |
| `restore.py` | (M2) проверка пинов, импорт хранилищ, регидрация сессии, residual-событие |
| `api.py` | FastAPI-роутер `/api/checkpoints/...`, монтируется на web-сервер и на A2A-приложение оркестратора |

**Механизм подключения — ADK-плагин + два явных вызова, без правок промптов и YAML.**
Плагин регистрируется в списках `plugins=[...]` (`main.py:178-185`,
`a2a/server.py:125-132`) — одна точка покрывает CLI, web и A2A. Явных вызова два,
оба в HITL-слое, потому что момент «до ревью» хукам не виден:
1. `SessionAgent._run_async_impl` — `await checkpoint_service.save(...)`
   непосредственно перед `await handler.handle_request(...)` (финальное событие
   буферизовано, хука нет — честное исключение);
2. для профиля без планировщика T0 ловится плагином через `before_tool_callback`
   по имени инструмента `request_approval`/`request_selection` — работает на любом
   входе, включая A2A-серверы подчинённых, и не зависит от подменяемого
   `hitl_toolset._handler`.

Сохранение синхронное, но дешёвое (JSON, КБ–МБ), обёрнуто в try/except:
**упавший чекпоинт логируется и никогда не роняет научный прогон**.

## 3. Модель данных чекпоинта

Содержимое снимка (исчерпывающе):

1. **Экспорт корневой сессии**: `app_name`, `user_id`, `session_id`; полный
   упорядоченный список событий `event.model_dump(exclude_none=True, mode="json")`
   (тот же формат, что у `DatabaseSessionService` — блобы совместимы с БД-бэкендом);
   **плюс триггерное событие, влитое вручную** (см. факт №1); **плюс авторитетный
   словарь состояния**, снятый с живой `ic.session.state` (см. факт №2).
   Ключи `temp:*` отбрасываются (сегодня их нет).
2. **Контекст оркестратора**: `active_tasks`/`planner_roadmap` уже в состоянии
   сессии; байтовая копия `task_tracker_data.json`; указатель `resume_from`
   `{module, label, next_action}` — вычисляется плагином из того, какая граница
   сработала (истории сессии недостаточно, чтобы система знала, что делать дальше).
3. **Хранилища модулей**: копии `research_active.json`, `graph_runs/<run_id>.json`,
   `knowledge_memory.json`; для микрофлюидики — структурированный ТЗ-документ.
4. **HITL pending** (только для pre-HITL точек): сериализованный `HITLRequest`
   (агент, тип, полезная нагрузка) — чтобы после восстановления заново показать
   ревью. Корутины и `asyncio.Future` не сериализуются никогда.
5. **Внешние ссылки, никогда не полезные нагрузки**: артефакты FEDOT как
   `{s3_key, bucket, columns}` (presigned-URL отбрасываются — протухают);
   `uploaded/downloaded_paper_s3_keys`; `filtered_tools` — `server_id` из
   Postgres-реестра MCP (перепроверяются при восстановлении); `deployed_mcps` —
   URL с пометкой `liveness: unverified`; FEDOT в полёте — `{status: "detached"}`;
   `coder_workspace_id` — как непрозрачная внешняя ссылка (кодер вне контура).
6. **Пины воспроизводимости**: путь профиля + SHA-256 разрешённого YAML; SHA-256
   `agents/prompts/templates.py`; идентификаторы моделей (`LLM__MAIN_MODEL` и др.);
   формирующие дерево env (`HITL__ENABLED`, `RESEARCH_GRAPH__ENABLED`,
   `ORCHESTRATOR__USE_PLANNER`, признаки наличия `MCP__*_URL`); git-коммит; версия
   google-adk. Дамп настроек проходит через существующий `_redact()`
   (`a2a/server.py:28`) — **значения секретов в бандл не попадают**.

Манифест (`manifest.json` в корне zip):

## 4. Хранение

**Вердикт по «одному файлу»: да — один zip-бандл на чекпоинт.** Суммарный объём
состояния в любой точке — единицы МБ максимум (события + 4 JSON-хранилища +
словарь состояния; данные и артефакты остаются в S3 по ссылкам). Дедупликация
между соседними чекпоинтами на этих объёмах не окупается и создаёт проблему GC
общих блобов — в M1 её нет.

```
checkpoints_data/
  <run_id>/
    index.json                          # id → label, ts, parent (восстановим из манифестов)
    ckpt_20260721T1402_T0.zip           # manifest.json + blobs/sha256-*
    ckpt_20260721T1408_T1.zip
```

Внутри zip блобы именуются по хэшу содержимого — это и есть хук совместимости
с платформой: переезд на MinIO = выгрузка `blobs/*` как объектов по тем же хэшам
и манифеста в реестр снимков, формат не меняется. Zip одновременно является
экспортным форматом («скачать состояние запуска» в UI) и форматом импорта.

Запись атомарна: сборка во временном файле → `os.replace`. Падение посреди
сохранения оставляет либо прежний полный набор бандлов, либо tmp-мусор —
никогда рваный zip. Отвергнуто: sqlite (лишняя схема для данных, которые уже
JSON), голая директория (теряет UX одного файла), переезд живых сессий на
`SqliteSessionService` (класс не экспортирован из ADK, а главное — прямые мутации
состояния до БД всё равно не доходят: «бесплатная durable-подложка» — иллюзия).

## 5. Логика сохранения: триггеры и точки покоя

Карта T-меток на реальный код. Основной режим M1 — in-process (web UI, CLI);
колонка remote — для режима `run_all` (пригодится при интеграции с Synapse).

| Метка | In-process (web/CLI) | A2A remote (`run_all`) |
|---|---|---|
| **T0 after_plan** (перед HITL-ревью плана) | Профиль с планировщиком: явный вызов в `SessionAgent._run_async_impl` перед `handle_request`. Профиль без планировщика: `before_tool_callback` на `request_approval`/`request_selection` (событие function_call уже закоммичено — продюсер блокируется на enqueue) | То же — `before_tool` работает на любом сервере и не зависит от подмены обработчика HITL |
| **T1 after_literature_review** | `on_event_callback`: в `state_delta` есть `search_results` (+ влить событие в экспорт) | `after_tool_callback` оркестратора на возврате делегации ResearchAgent |
| **T2 after_hypotheses** | то же, ключ `hypotheses` | `after_tool` на возврате делегации HypothesesAgent |
| **T3 before_experiment** | **`before_agent_callback` на `ExperimentAgent`** — единственный работающий триггер: дельты `deployed_mcps` НЕ существует (прямая мутация, факт №2) | `before_tool` оркестратора на делегации модуля экспериментов |
| **T4 after_experiment** | `on_event_callback`, ключ `fedot_results` | `after_tool` на возврате делегации |
| **T5 before_report_release** | `after_run_callback` (инвокация завершена, граница хода пользователя) | то же |

Замечания:
- В remote-режиме триггеры по `state_delta` мертвы by design: `RemoteA2aAgent`
  собирается без `output_key`, дельты остаются в сессиях подчинённых серверов.
  Универсальный сигнал границы модуля — **возврат инструмента-делегации у
  оркестратора**; карта меток — конфигурационный словарь, не код на профиль.
- Дельты `coder_results` — сознательно не триггер (кодер вне контура).
- **Квиесценция**: `on_event_callback`/`after_tool` срабатывают, когда производящий
  агент полностью закончил шаг; история до N-1 закоммичена; исполнение — одна
  asyncio-задача на инвокацию, значит в этот момент никто не в середине шага.
  Плагин дополнительно не снимает чекпоинт, пока активен `fedot_tool` или
  незавершённая делегация (учёт через `before/after_tool`).
- Допустимый остаток асинхронности: fire-and-forget задачи
  `BackgroundValidatorPlugin` могут долететь после снимка — безопасно (вердикты
  восстановимы из графа исследования), в манифесте `validator_pending: true`,
  восстановление перезапускает валидацию.

## 6. Логика восстановления через A2A

**Принцип: восстановление = всегда новый экземпляр запуска** (контракт Synapse
§6.6.1). Живой процесс не мутируется; API отказывает (409), пока есть активная
инвокация.

**Первичный канал — служебный REST-роутер** `checkpoints/api.py`, смонтированный
на web-приложение и на A2A-приложение оркестратора (результат
`A2AFastAPIApplication.build()` — обычный FastAPI). Команды управления не должны
проходить через интерпретацию текста моделью; это дословно позиция Synapse
(«первичен API»). Возможность объявляется в AgentCard расширением:
`AgentExtension(uri="urn:coscientist:ext:checkpoint:v1", params={"api": "/api/checkpoints"})`.

Последовательность:

```
1. GET  /api/checkpoints?run_id=...          → список точек с метками T0–T5
2. POST /api/checkpoints/{id}/restore        body: {"mode": "fork"|"restore",
                                                    "compat": "strict"|"relaxed"}
   a. Гейт занятости: активная инвокация → 409.
   b. Гейт пинов: сверка profile_sha256 / prompts_sha256 / моделей / env
      с живым процессом. strict → 409 с диффом; relaxed (по умолчанию для fork)
      → предупреждения в ответе; ?force=true — явное переопределение, логируется.
   c. Новая identity: new_context_id = f"restore-{ckpt[:8]}-{uuid4().hex[:8]}";
      user_id = f"A2A_USER_{new_context_id}"  ← ОБЯЗАН совпадать с фолбэком ADK
      (request_converter.py:66-76), иначе следующее сообщение не найдёт сессию.
   d. Импорт хранилищ: task_tracker_data.json → перезагрузка синглтона;
      research_active.json → import_state() с архивацией текущего;
      граф выполнения → под новым run_id (web UI обязан переключить KG_RUN_ID).
   e. Регидрация сессии (точные вызовы ADK 2.3.0):
        s = await svc.create_session(app_name=key, user_id=uid,
                                     session_id=new_context_id, state={})
        for ev in events_blob:                       # id/timestamp дословно
            await svc.append_event(s, Event.model_validate(ev))
        residual = saved_state − replayed_state      # несущий шаг, не защитный:
        await svc.append_event(s, Event(author="system",  # доносит deployed_mcps,
            actions=EventActions(state_delta=residual)))  # правки плана и т.п.
        s = await svc.get_session(...)
   f. Сверка внешнего: server_id инструментов — по живому Postgres-реестру MCP,
      расхождения → предупреждение (оркестратор перезапустит ToolPreparer,
      путь NO_MATCHING_TOOL уже существует); deployed_mcps — health-check;
      S3 — re-presign по устойчивым ключам; FEDOT — всегда detached.
   g. Ответ: {"context_id": ..., "resume_hint": ..., "hitl_pending": ...,
              "warnings": [...]}.
3. Клиент шлёт обычный A2A message/send с contextId = new_context_id.
   _prepare_session находит регидрированную сессию; _find_agent_to_run
   маршрутизирует по истории; выпускается НОВЫЙ taskId (терминальные задачи A2A
   неизменяемы; продолжение = новая задача в контексте, referenceTaskIds — по
   желанию). Текст сообщения UI предзаполняет из resume_hint.
```

**Особый случай T0 (pre-HITL).** В бандле профиля без планировщика история
заканчивается закоммиченным `function_call` без ответа. Реплеить его нельзя —
история с висящим tool_call ломает LiteLLM/OpenAI-путь. Решение: **при
восстановлении висящий function_call усекается**, UI заново показывает ревью из
`hitl_pending`, решение оператора уходит обычным сообщением — оркестратор заново
проходит ворота (повторный запуск гейта дёшев и идемпотентен; та же доктрина, что
у interrupt в LangGraph). Альтернатива (синтетический `FunctionResponse` с
сохранённым `function_call.id`) документирована как вариант, если повторный проход
ворот окажется нежелателен.

**Fork vs restore**: fork — основной научный режим (старая ветвь живёт, копится
дерево вариантов); restore — тот же fork + пометка новой ветви «текущей» в
`index.json`. Родословная — `parent_checkpoint_id` в манифесте первого чекпоинта
новой ветви. `replay(strict)` отложен: требует записанных ответов моделей — его
естественное место в журнале платформы (Synapse §6.4.4).

**Что нужно web UI**: панель чекпоинтов (список + таймлайн, кнопки fork/restore,
скачивание бандла); параметризация `session_id` в `CoScientistManager`
(сейчас захардкожен `session_001`, `main.py:120-129`) и переключение активного
run_id для `/api/graph` — иначе граф выполнения после восстановления рассинхронизируется.

**Холодный старт** (процесс упал): поднять сервер с пином env из манифеста →
вызвать restore → продолжить. Регидрация на `InMemorySessionService` означает, что
восстановленный запуск живёт до следующего T-чекпоинта — этого достаточно,
т.к. бандлы на границах и есть наша durable-подложка.

## 7. Динамические саб-агенты: что сохраняем

**Решение: только контекст исполнения оркестраторов (сессия + состояние + план +
хранилища модулей). Промежуточное состояние саб-агентов не сохраняется вовсе.**

Обоснование из устройства репозитория:
1. Дерево агентов фиксировано на сборке (`assembler.py:281` — единственное
   `sub_agents=`); в рантайме структура не мутирует. Пересборка из того же
   профиля + пинов гарантированно даёт то же дерево (гейт пинов 6.2b).
2. Настоящая динамика — **поверхность инструментов**, и она целиком данные:
   `filtered_tools`/`deployed_mcps` в состоянии сессии, `DynamicMCPToolset`
   пересчитывает на каждом ходу. Восстановили ключи — восстановили выбор
   инструментов (с перепроверкой по живому реестру).
3. Саб-агенты между вызовами не имеют скрытого состояния: результаты возвращаются
   через `AgentTool`/`output_key` и оседают в сессии оркестратора. На T-точках
   любая делегация уже вернулась. Прерванная делегация просто перезапускается
   с последнего закоммиченного шага оркестратора — дешевле и надёжнее, чем
   сериализовать полуготовый LLM-цикл ребёнка.
4. В A2A-режиме сессии подчинённых серверов — одноразовые, на делегацию;
   восстановленный оркестратор создаст новые.
5. Если в будущем планировщик начнёт конструировать агентов в рантайме — включаем
   AutoGen-схему «декларативная спецификация рядом с состоянием» (слот `subagents`
   в манифесте уже зарезервирован). Сегодня ни один код-путь этого не требует.

**Не сохраняем и не будем**: окружение кодер-агента (`workspace/`, контейнеры) —
ждёт постоянного сендбокса; внутренний Runner FEDOT (in-memory, недостижим by
design — политика detach); содержимое артефакт-сервиса ADK — файлы, приложенные
через web-чат, должны уезжать в S3 и попадать в чекпоинт устойчивыми ключами
(открытый вопрос №5).

## 10. Риски и открытые вопросы

1. **Процесс-глобальные синглтоны** (граф исследования, task_tracker, `_system`,
   web `session_001`): восстановление в занятый процесс клоббирует состояние.
   → 409-гейт занятости; архивация перед импортом; рекомендация — restore в свежий
   процесс; параметризация путей хранилищ по run_id — кандидат на M2b.
2. **Дрейф конфигурации/промптов**: инструкции запекаются при сборке — чекпоинт
   под другим профилем молча меняет поведение. → обязательный гейт пинов с диффом,
   `force` — явный и логируемый.
3. **Распад внешних ссылок**: `server_id` может исчезнуть из реестра MCP,
   `deployed_mcps` — умереть, presigned URL — протухнуть. → перепроверка и
   health-check на restore, предупреждения в ответе; хранить только устойчивые
   `s3_key`+`bucket`; открытый вопрос — подавлять S3-очистку
   (`manager.close()` удаляет префиксы загруженных статей) для чекпоинтнутых
   запусков или копировать объекты в префикс чекпоинта (рекомендация: копировать,
   объёмы малы).
4. **Профили с SequentialAgent-корнем (микрофлюидика)**: новая инвокация
   перезапускает детей с первого — `agent_state`/`end_of_agent` реплеятся только
   при возобновлении той же инвокации под `ResumabilityConfig`. Для M1/M2
   восстановление таких профилей документируется как «повторный проход модуля с
   восстановленным состоянием» (идемпотентно за счёт состояния); первоклассное
   решение — включение resumability, отдельная задача.
5. **Файлы из web-чата** живут в `InMemoryArtifactService` и в бандл не попадают.
   → M1: фиксировать в манифесте предупреждение при наличии артефактов;
   M2: складывать вложения в S3 при приёме и включать ключи в `external`.
6. **Эндпоинты `/api/checkpoints/*` не аутентифицированы** — как и весь
   остальной API проекта (web UI, A2A-серверы, graph-сервис): аутентификации
   в системе пока нет нигде. Restore защищён только гейтом занятости.
   → закрывается контуром безопасности платформы Synapse (П-10) при
   интеграции; до тех пор — не выставлять порты наружу.

## 11. Статус реализации (2026-07-22)

Реализовано (M1 + ядро M2), e2e через A2A проходит: запуск → автоснимки
T1/T5 → kill процесса → restore в свежем процессе через REST → продолжение
обычным `message/send`; выживают и дельта-ключи, и прямые мутации; restore
T1 корректно возвращает состояние «до мутации» (`tests/e2e_checkpoint_a2a.py`).

Код: пакет `checkpoints/` (model, store, capture, plugin, restore, api, hooks);
подключение: `a2a/server.py` (плагин + роутер), `main.py` (плагин),
`hitl/session_agent.py` (явный T0-хук), `web/app.py` (роутер + уникальный
session_id на диалог + перенаправление чата на восстановленную сессию),
`config/settings.py` (`CHECKPOINTS__ENABLED` / `CHECKPOINTS__DIR`, по
умолчанию выключено). Зависимость `a2a-sdk==0.3.26` добавлена в pyproject/lock.

Уточнения дизайна по итогам адверсариального ревью реализации (26 агентов):
- редакция состояния — по **токенам** имени ключа, не по подстроке
  (`uploaded_paper_s3_keys` не должен превращаться в `***redacted***` в
  авторитетном блобе); `external` считается из сырого состояния;
- дочерние раннеры `AgentTool` (делегации) наследуют плагины ADK — плагин
  распознаёт их по идентичности session_service и не снимает с них снимков;
- гейт занятости restore — **процессный** (`CheckpointPlugin.any_busy()`):
  в `run_all` шесть серверов делят один процесс и одни синглтоны-хранилища;
- счётчик «инструмент в полёте» освобождается и в `on_tool_error_callback`
  (ADK не вызывает `after_tool` при исключении) и принудительно на границе
  хода; busy-записи протухают через час (legacy-путь Runner может пропустить
  `after_run` при исключении);
- усечение висящих `function_call` при restore обобщено на любые инструменты
  (упавший ход тоже оставляет неотвеченный вызов), не только HITL;
- `validator_pending` заполняется по факту незавершённых задач фонового
  валидатора.

Осталось на будущее: панель чекпоинтов в web UI (API уже смонтирован),
перенос вложений web-чата в S3, ResumabilityConfig для sequential-профилей,
строгий replay, аутентификация через контур платформы.
