

## 0. Задачи сторон (тезисно)

**Платформа Synapse обеспечивает:**

1. Фронтенд и API: постановка задачи и выбор МАС с профилем конфигурации; лента событий; вопросы и согласования; артефакты; таймлайн контрольных точек с ветвлением «отсюда»; дерево запусков; состояние MCP-серверов.
2. Реестр пакетов МАС, их версий и профилей конфигурации; порождение A2A-карточек (AgentCard) из манифестов.
3. Run-контроллер — управление запусками внешних МАС по A2A: старт, поток событий, команды, отмена, возобновление, завершение.
4. Журнал событий как источник истины: приём потока A2A, присвоение порядковых номеров, доставка в интерфейс, дочитывание после обрывов.
5. Хранилище артефактов с происхождением; хранилище снимков состояния; родословную (дерево) запусков; API отката: restore / fork / replay.
6. MCP-контур: реестр и шлюз инструментов (рекомендуется IBM ContextForge), развёртывание MCP-серверов до старта МАС, маршрутизация и журналирование вызовов, внедрение секретов, проверка совместимости версий.
7. Ресурсы институтских кластеров: песочницы, задания Kubernetes/Ray, очереди и квоты GPU, учёт потребления, бюджеты вызовов моделей.
8. Безопасность: контекст запуска, секреты, изоляция, мультиарендность; сквозная трассировка.

**Подключаемая МАС (CoScientist — первая) обеспечивает:**

1. Манифест пакета с профилями конфигурации (основная реализация, «Микрофлюидика», испытательные наборы).
2. Адаптер-сервис: один A2A-сервис на всю систему (одна карточка) плюс служебные эндпоинты управления и снимков.
3. Поток событий платформенного словаря поверх A2A (упаковка внутренних событий в части данных).
4. Дисциплину состояния: сеансы в постоянном хранилище; интерфейс выгрузки состояния у мастер-оркестратора и модулей; барьер и точки покоя; снимки на границах модулей (T0–T5); фильтр секретов.
5. Артефакты и вызовы инструментов — только через платформу; формальный experiment_spec; версии промптов и моделей; зёрна случайности из конфигурации запуска.
6. Научную логику без изменений: модули, RAG-подбор инструментов, FEDOT — не затрагиваются; добавляется только обвязка.

## 1. Общие положения

### 1.1. Назначение документа

Документ определяет требования к платформе для мультиагентных систем (далее — платформа) и порядок подключения к ней научной МАС CoScientist. Платформа остаётся на собственном движке Synapse; переход платформы на какую-либо иную среду (в том числе ADK) настоящим документом не предполагается и не требуется. CoScientist подключается как внешняя МАС — тем же способом, каким будут подключаться и другие системы на иных движках. Внутренний движок каждой МАС (у CoScientist — Google ADK) — её частное дело, скрытое за адаптером.

Цель интеграции: CoScientist остаётся самостоятельной научной системой со своей внутренней логикой (порождение гипотез, планирование экспериментов, подбор инструментов), а платформа берёт на себя общесистемные функции — запуск и жизненный цикл, наблюдение, управление состоянием и откатом, ресурсы кластеров, хранение артефактов, безопасность и учёт.

### 1.2. Термины и сокращения

| Термин | Значение |
|---|---|
| МАС | Мультиагентная система — совокупность агентов с собственной оркестровкой подзадач |
| Модуль МАС | Крупный блок МАС со своим агентом-оркестратором (в CoScientist: литературный анализ, гипотезы, эксперименты, отчёты) |
| Профиль конфигурации | Именованный состав МАС: набор модулей, инструментов, промптов и ресурсов (например, «Микрофлюидика») |
| Запуск (run) | Единичное исполнение МАС с заданными входом, версией, профилем и ограничителями |
| Сеанс (session) | Единица хранения истории и состояния диалога внутри движка МАС |
| Контрольная точка, снимок состояния (checkpoint) | Согласованный слепок состояния запуска, достаточный для продолжения работы с этого места |
| Откат (rewind) | Возврат работы к контрольной точке |
| Ветвление (fork) | Порождение нового запуска от контрольной точки при сохранении исходного |
| Воспроизведение (replay) | Повторное исполнение от контрольной точки или от начала |
| Точка покоя | Момент, когда ни один агент не находится в середине незавершённого шага |
| Адаптер | Сервис на стороне МАС, реализующий платформенный контракт (A2A + служебный API) |
| Run-контроллер | Алгоритмический компонент платформы, управляющий жизненным циклом запусков |
| Манифест | Декларативное описание пакета МАС либо снимка состояния |
| Артефакт | Порождённый в ходе запуска файл или набор данных: отчёт, датасет, модель, график |
| Происхождение (provenance) | Сведения о том, кем, когда, из чего и какими версиями порождён результат |
| Журнал событий | Пополняемая только добавлением последовательность событий; источник истины |
| Согласование (approval) | Остановка исполнения до явного решения человека |
| Шлюз | Единая управляемая точка прохождения обращений (к инструментам, агентам, моделям) |
| A2A | Agent2Agent — открытый протокол взаимодействия агентов |
| MCP | Model Context Protocol — стандарт подключения агентов к инструментам и данным |
| OTel | OpenTelemetry — стандарт трассировки и метрик |

### 1.3. Разграничение ответственности

Основополагающий принцип — **принцип непрозрачной МАС**: платформа не знает внутреннего устройства подключаемой системы. Ей достаточно знать: что система умеет; как её вызвать; какие входы и выходы; как читать поток событий; какие артефакты создаются; какие права, секреты и ресурсы нужны; как остановить, возобновить и откатить.

| Платформа отвечает за | Подключаемая МАС отвечает за |
|---|---|
| Запуск, остановку, возобновление, жизненный цикл | Научную (прикладную) логику целиком |
| Пользователей, проекты, права, мультиарендность | Внутреннюю оркестровку модулей и агентов |
| Реестр пакетов, версии, профили, развёртывание | Содержимое профилей конфигурации |
| Журнал событий, трассировку, аудит | Честный и полный поток событий |
| Хранение артефактов и снимков, родословную запусков | Содержимое снимков собственного состояния |
| Развёртывание и жизненный цикл MCP-серверов | Разработку самих MCP-инструментов |
| Песочницы, кластеры CPU/GPU, очереди, бюджеты | Формальное описание экспериментов |
| Согласования как механизм | Выбор мест, где согласование требуется |

Платформа управляет тем, **как исполнять**; МАС решает, **что делать**.

## 2. Целевая архитектура

### 2.1. Слои

```
Платформа Synapse (собственный движок)
│
├── Управляющий контур (Control Plane)
│   ├── реестр МАС: пакеты, версии, профили
│   ├── Run-контроллер (алгоритмический)
│   ├── пользователи, проекты, права, квоты
│   ├── согласования (участие человека)
│   └── журнал, трассировка, аудит, учёт
│
├── Слой взаимодействия (Interoperability Layer)
│   ├── A2A-клиент/шлюз      — диалог с подключёнными МАС
│   ├── MCP-контур           — реестр, шлюз и развёртывание инструментов
│   └── REST + SSE           — фронтенд и внешние потребители
│
├── Слой подключённых МАС (внешние сервисы; платформа их НЕ исполняет внутри себя)
│   ├── CoScientist    — контейнер: адаптер + внутренний движок ADK
│   ├── МАС на LangGraph — контейнер: адаптер + движок LangGraph
│   ├── МАС на ином движке — контейнер: адаптер + свой движок
│   └── встроенные агенты Synapse — собственный движок платформы (её частные сценарии)
│
└── Слой заданий, артефактов и происхождения
    ├── задания Docker / Kubernetes / Ray (эксперименты, песочницы)
    ├── объектное хранилище: артефакты, части снимков
    ├── наборы данных и метаданные экспериментов
    └── обеспечение воспроизводимости
```

Ключевое отличие от модели «агенты живут внутри платформы»: подключаемые МАС — внешние сервисы со своими движками. Платформа их разворачивает, запускает и сопровождает, но не исполняет их логику своим движком и не требует переписывания под себя.

### 2.2. Три сущности: инструмент, агент, МАС

```
Инструмент = функция / API / вычислительная операция без диалогового состояния
Агент      = автономный исполнитель с состоянием, диалогом и политикой
МАС        = группа агентов, самостоятельно оркеструющая подзадачи
```

Полноценную МАС нельзя сводить к инструменту: у неё есть состояние, диалог, планирование, подагенты, длительные операции, уточняющие вопросы и участие человека. Поэтому подключение строится через протокол взаимодействия агентов (A2A) и адаптеры, а не через приведение всех систем к одному внутреннему формату.

### 2.3. Распределение протоколов

| Задача | Что использовать |
|---|---|
| Платформа ↔ подключённая МАС | **A2A** (диалог, задачи, поток) + служебный API адаптера (управление, снимки) |
| Агент ↔ инструменты и данные | **MCP** через шлюз платформы |
| Фронтенд ↔ платформа | REST + SSE из журнала платформы |
| Трассировка и метрики | OpenTelemetry |
| Артефакты и снимки | Объектное хранилище (MinIO) + манифесты |

### 2.4. Схема подключения

```
                ┌───────────────────────────┐
                │  Фронтенд платформы       │
                └────────────┬──────────────┘
                             │ REST + SSE (журнал платформы)
                ┌────────────▼──────────────┐
                │  Управляющий контур       │
                │  Synapse: Run-контроллер, │
                │  реестр, журнал,          │
                │  согласования, учёт       │
                └───────┬───────────┬───────┘
                        │           │
                  A2A-клиент     MCP-контур (реестр + шлюз + развёртыватель)
                        │           │
        ┌───────────────┤           ├───────────────────┐
        │               │           │                   │
┌───────▼────────┐      │   ┌───────▼────────┐  ┌───────▼────────┐
│ CoScientist    │      │   │ MCP-серверы    │  │ MCP-серверы    │
│ (контейнер:    │      │   │ CoScientist    │  │ общего         │
│  адаптер + ADK)│      │   │ (развёрнуты    │  │ назначения     │
└────────────────┘      │   │  платформой)   │  └────────────────┘
                ┌───────▼────────┐
                │ Другая МАС     │
                │ (контейнер:    │
                │  адаптер + свой│
                │  движок)       │
                └────────────────┘
```

Адаптер — часть поставки МАС и работает в её контейнере; на стороне платформы адаптеров нет, есть единый контракт.

### 2.5. Принципиальные архитектурные решения

**А-1. Контрактный слой вместо единого внутреннего формата.** Универсальность достигается внешним контрактом (манифест, A2A, служебный API, события, артефакты, снимки), а не переписыванием МАС под движок платформы. Движок каждой МАС — её внутреннее дело.

**А-2. Неизменяемые запуски.** История запуска не переписывается; откат порождает новую ветвь; исходный запуск и журнал сохраняются целиком.

**А-3. Журнал событий — источник истины.** Потоковая доставка — лишь средство своевременного оповещения; критическое состояние подтверждается журналом и опросом задач.

**А-4. Восстановление состояния выполняет сама МАС.** Платформа хранит и передаёт снимки, но не разбирает их содержимое.

**А-5. Все внешние действия МАС проходят через контуры платформы** — инструменты через MCP-шлюз, тяжёлые вычисления через шлюз заданий. Иначе невозможны учёт, происхождение, воспроизводимость и компенсации.

**А-6. MCP-серверы — управляемые сервисы платформы**, развёртываемые **до** запуска МАС по декларации в манифесте.

**А-7. Сначала контракты, потом код.** Схемы манифеста, событий и снимков согласуются и версионируются раньше реализации.

**А-8. Управление запусками — алгоритмическое.** Run-контроллер — детерминированный сервис; LLM-агенты платформы в запуске и надзоре за внешними МАС не участвуют.

## 3. Модель подключения МАС и управления со стороны платформы

Раздел отвечает на четыре проектных вопроса: какова гранулярность A2A; как платформа управляет CoScientist; как течёт поток событий; когда и кем создаются и выбираются контрольные точки.

### 3.1. Гранулярность подключения: одна МАС — один агент-сервис A2A

Каждого внутреннего агента CoScientist выставлять по A2A **не нужно**. Вся МАС — один агент-сервис: одна карточка AgentCard, один A2A-эндпоинт, один адаптер. Обоснование:

1. Внутренние агенты разделяют общий контекст — сеансы, словарь состояния, план мастер-оркестратора. Обращение к «агенту гипотез» в обход мастера нарушило бы инварианты, за которые платформа не отвечает и отвечать не может (принцип непрозрачной МАС).
2. N карточек породили бы N параллельных машин состояний задач A2A, которые платформе пришлось бы согласовывать между собой, — сложность без выгоды.
3. Откат в любом случае общесистемный: снимок охватывает состояние всей системы (раздел 6), потому что состояния модулей связаны — гипотезы опираются на литературный анализ, эксперимент на гипотезы.

Модульная структура при этом не теряется. Модульные оркестраторы видимы платформе через поле `agent` в событиях и через **метки контрольных точек** («после литературного анализа», «после гипотез»). Этого достаточно и для интерфейса, и для откатов. Если потребуется запускать модуль отдельно (только литературный обзор), это оформляется профилем конфигурации той же МАС (3.5), а не отдельным A2A-агентом.

```
Видимо платформе:                  Скрыто внутри CoScientist:

AgentCard «CoScientist»            Мастер-оркестратор
один A2A-эндпоинт                  ├── Модуль литературного анализа (оркестратор + подагенты)
один поток задач и событий         ├── Модуль гипотез
метки точек: T0…T5                 ├── Модуль экспериментов
                                   └── Модуль отчётов
```

### 3.2. Управление запуском: алгоритмический Run-контроллер, а не агент

Запуск, надзор и остановка внешних МАС — детерминированный сервисный код платформы. Создавать платформенного LLM-агента «на каждый оркестратор CoScientist» не нужно; не нужен и один агент «на всю систему»: рассуждающая модель в контуре управления добавляет недетерминизм ровно там, где требуются предсказуемость, идемпотентность и воспроизводимость. Встроенные агенты Synapse остаются для собственных сценариев платформы и в управлении внешними МАС не участвуют (А-8).

Цикл Run-контроллера для одного запуска:

```
создать запуск (run_id; версия, профиль, ограничители, контекст безопасности)
  → подготовить MCP-серверы по манифесту (П-6)             ┐ до старта МАС
  → развернуть/найти экземпляр МАС нужной версии            ┘
  → A2A message/send: входная задача        → зафиксировать run_id ↔ contextId/taskId
  → A2A message/stream: подписка            → журнал платформы (присвоение seq)
  → трансляция команд по ходу работы:
      отмена                                → tasks/cancel
      ответ на вопрос, решение согласования → message/send (тот же taskId)
      снимок / restore / fork / replay      → служебный API адаптера (6.8)
  → завершение: финальные артефакты, гашение dedicated-ресурсов, учёт
```

Решение «какой модуль запустить следующим по плану» принимает мастер-оркестратор CoScientist — это научная логика, она остаётся внутри МАС.

### 3.3. Поток событий: как именно МАС передаёт происходящее

Основной канал — потоковый режим A2A (`message/stream`, доставка по SSE): статусные события задачи (submitted → working → input-required → …), события артефактов и, в структурированных частях данных, события платформенного словаря (П-3.4) вместе с доменными `domain.*`. Адаптер упаковывает каждое внутреннее событие CoScientist в часть данных A2A; Run-контроллер разворачивает их, присваивает `seq` и пишет в журнал; фронтенд читает **журнал платформы** через её собственный SSE, а не сырой поток A2A.

```
CoScientist ──A2A SSE──▶ Run-контроллер ──запись──▶ Журнал (seq) ──SSE──▶ Фронтенд
 (адаптер)                     │                        ▲
                               └── tasks/resubscribe ───┘  дочитка по seq после обрыва
```

Обрывы безопасны: A2A даёт повторную подписку на задачу (`tasks/resubscribe`), недостающее дочитывается из журнала по `seq` (А-3). Для многочасовых запусков в дополнение допускаются push-уведомления A2A.

### 3.4. Чат с системой, точки согласования и момент отката

**Как устроен чат через один A2A-сервис.** A2A — изначально диалоговый протокол: `contextId` держит многоходовую беседу, а состояние задачи `input-required` существует ровно для случая «система спрашивает — человек отвечает». Сообщение пользователя из чата фронтенда Run-контроллер передаёт как `message/send` с тем же `taskId`; адаптер вручает его мастер-оркестратору. В обратную сторону всё, что система хочет показать (текст плана, гипотезы, вопросы), уходит сообщениями и артефактами A2A вместе с событиями, ложится в журнал — и чат фронтенда есть проекция журнала. «Голосом» системы выступает мастер-оркестратор; отдельные чаты с внутренними агентами не нужны и противоречили бы 3.1.

**Точка сохранения ≠ точка согласования.** Снимки дёшевы, автоматичны и работу не останавливают: границы T1, T2, T4 обычно проходятся молча. Точка согласования — осознанная остановка по политике: мастер-оркестратор доходит до ворот, порождает `approval.requested` с контекстом решения (сам план — артефактом, оценка стоимости, обратимость), переводит задачу A2A в `input-required`, запуск — в `waiting_input`, и приостанавливает исполнение — ожидание решения в точке покоя, без «горячего» цикла. Свежий автоснимок перед воротами уже лежит (П-9.3). Правило: **каждое согласование опирается на снимок, но не каждый снимок требует согласования** — иначе система потеряла бы автономность и длинные прогоны «на ночь» стали бы невозможны.

Поток для примера «согласование плана»:

```
Мастер-оркестратор построил план
  → снимок chk_T0 (автоматически, без остановки)
  → политика: план требует согласования
  → approval.requested {план-артефакт, оценка стоимости}
  → задача A2A: input-required · запуск: waiting_input · исполнение приостановлено
  → чат фронтенда: план + действия
        ├── «Согласовать»             → message/send {решение} → resume → running
        ├── «Замечания» (текст в чат) → message/send → оркестратор дорабатывает план
        │                               → новые ворота (цикл до согласия)
        └── «Откатиться к точке…»     → fork от выбранного снимка → новый запуск
```

**Откат не привязан к паузам.** Благодаря неизменяемым запускам (А-2) ветвление от любой прошлой точки доступно всегда — даже пока запуск работает (исходный при желании отменяется). Пауза нужна для решения «двигаться ли вперёд и как», а не для самой возможности отката; на воротах «откатиться» — просто одно из действий рядом с «согласовать» и «замечания». Фронтенд показывает таймлайн точек (6.3) и на воротах, и в любой другой момент.

**Где ставить ворота** — политика согласований (П-9.2), а не жёсткая привязка к каждой точке. Для научного сценария естественны ворота на плане (T0), перед дорогим экспериментом (T3) и перед выпуском отчёта (T5); границы T1, T2, T4 проходят со снимком, но без остановки. Режим «ручной» превращает все границы модулей в ворота, «автоматический» убирает остановки вовсе.

**Сообщения пользователя вне ворот.** Если пользователь пишет в чат, пока запуск в `running`, адаптер ставит сообщение в очередь, и мастер-оркестратор читает её на ближайшей точке покоя (границе шага или модуля): вмешаться посреди вызова модели невозможно по той же причине, по которой там невозможен снимок. Долгое ожидание на воротах допускает гашение dedicated-ресурсов: раз перед воротами есть снимок, возобновление устроено как восстановление из него (6.6) — ещё одно следствие дисциплины К-8.

### 3.5. Профили конфигурации МАС

CoScientist существует в нескольких составах: основная реализация, проект «Микрофлюидика», испытательные наборы. Манифест объявляет **профили конфигурации** (`config_profiles`); профиль может менять состав модулей, набор инструментов, промпты и ресурсные потребности. Запуск закрепляет пару «версия + профиль»; снимок несёт профиль, восстановление проверяет его совместимость. Для платформы профиль — непрозрачный идентификатор со своими зависимостями: содержимое профиля — дело МАС.

## 4. Технологическая основа

### 4.1. Протоколы

**A2A (Agent2Agent).** Открытый протокол взаимодействия агентов (Linux Foundation). Платформе даёт: карточку агента; задачу с жизненным циклом `submitted → working → input-required → completed / failed / canceled`; сообщения с частями (текст, данные, файлы); артефакты; потоковую доставку и повторную подписку; push-уведомления; расширения в карточке. Принципиальное ограничение по замыслу: внутреннее состояние агента непрозрачно. Следствия: `tasks/cancel` останавливает, но не откатывает (раздел 6); потоковые сообщения — не надёжный носитель истины, истина в журнале (А-3).

**MCP (Model Context Protocol).** Стандарт подключения агентов к инструментам и данным: JSON-RPC, примитивы tools / resources / prompts, транспорты stdio и streamable HTTP. Канал «агент ↔ инструменты», не канал «МАС ↔ МАС».

**OpenTelemetry.** Трассировка и метрики; семантические соглашения для генеративного ИИ; сквозные `run_id` и `trace_id` от фронтенда до задания на кластере.

### 4.2. Движки подключаемых МАС (справочно — платформа их не исполняет)

**Google ADK** — внутренний движок CoScientist. Для контракта существенно: сеансы и словарь состояния в SessionService (для снимков CoScientist переходит на постоянную реализацию — DatabaseSessionService либо совместимую); история как последовательность событий; обратные вызовы до/после агента, модели и инструмента — точка съёма событий для адаптера. Всё это скрыто за адаптером; платформа с ADK напрямую не работает.

**LangGraph** — граф состояний со встроенными контрольными точками и ветвлением; одновременно образец модели снимков и будущий тип подключаемых МАС.

**Pydantic AI, CrewAI и прочие** — подключаются тем же контрактом: адаптер + A2A; глубина реализации снимков зависит от возможностей движка и объявляется в манифесте.

### 4.3. Исполнение на кластерах института

**Kubernetes** — развёртывание служб платформы, MCP-серверов, экземпляров МАС, заданий экспериментов. Очереди и квоты GPU — **Kueue** либо **Volcano** (выбор на этапе 3 по испытаниям). **Ray** — распределённые вычислительные эксперименты (FEDOT, переборы), задания порождаются только через шлюз заданий платформы. **container-use** (уже в Synapse) — песочницы для порождаемого агентами кода.

### 4.4. Долговечность управляющего контура

**Temporal** — кандидат для устойчивости Run-контроллера к перезапускам (таймеры, повторы, компенсации). Решение на этапе 3; до того достаточно журнала в MongoDB и идемпотентных обработчиков. Не смешивать с снимками МАС: это механизмы разных уровней.

### 4.5. Хранилища

**MongoDB** — журнал, реестры, соответствия идентификаторов (есть в Synapse). **MinIO** — артефакты и части снимков, адресация по содержимому (sha256), политики хранения. **Redis** — по надобности, не обязателен на старте.

### 4.6. MCP-контур: рекомендация по ContextForge

Рекомендуемая основа — **IBM ContextForge MCP Gateway** (github.com/IBM/mcp-context-forge, Apache-2.0): реестр серверов и инструментов, виртуальные серверы, единая точка входа REST/MCP, управление доступом, федерация реестров; разворачивается в закрытом контуре (контейнер, Kubernetes). Разделение труда: ContextForge закрывает **реестр, маршрутизацию и доступ**; платформа добавляет тонкий **развёртыватель** — читает `requires.tools` манифеста, создаёт недостающие Deployment/Service в Kubernetes, дожидается готовности, регистрирует серверы в ContextForge и выдаёт МАС адрес шлюза. Существующий модуль `mcp_packages` Synapse сводится к развёртывателю и учёту пакетов. Допустимая альтернатива на этап 1 — собственный тонкий шлюз с переходом на ContextForge по мере роста номенклатуры инструментов; решение закрепляется по итогам этапа 1.

### 4.7. Наблюдаемость

**OpenTelemetry + Jaeger** (есть в Synapse) — сохраняются. По усмотрению — **Langfuse** либо **Arize Phoenix** (обе в закрытом контуре) для LLM-аналитики: стоимость по запускам и агентам, длины контекстов.

## 5. Требования к платформе Synapse

Требования нумеруются «П-x.y». «Обязана» — к этапам 0–2 плана (раздел 8), «следует» — к этапу 3, «допускается» — необязательная возможность.

### 5.1. Реестр МАС, манифест пакета, профили

- **П-1.1.** Платформа обязана вести реестр подключённых МАС: идентификатор, версии, профили, владелец, состояние, ссылки на манифесты.
- **П-1.2.** Манифест пакета обязан описывать: идентификатор и версию; точку входа (образ адаптера); схемы входа и выхода; возможности; профили конфигурации; потребности в MCP-инструментах, секретах и ресурсах; контракты событий, артефактов и снимков. Полный пример — приложение А.
- **П-1.3.** Версионирование семантическое; версии сосуществуют; запуск закрепляет пару «версия + профиль».
- **П-1.4.** Реестр порождает AgentCard из манифеста автоматически: одно описание — два представления.
- **П-1.5.** Профили конфигурации: платформа хранит перечень профилей МАС, отображает их при постановке задачи и передаёт выбранный профиль адаптеру при старте; содержимое профиля для платформы непрозрачно.

### 5.2. Управление запусками (Run-контроллер)

- **П-2.1.** Набор операций, который платформа предоставляет наружу, а адаптер МАС реализует со своей стороны:

```
describe        — описание возможностей (из манифеста)
start_run       — создать запуск (версия, профиль, вход, ограничители, контекст безопасности)
send_message    — сообщение / уточнение / решение согласования
stream_events   — поток событий
get_state       — текущее состояние запуска
cancel_run      — остановить
resume_run      — продолжить после паузы или согласования
list_artifacts  — перечень артефактов
get_trace       — трасса выполнения
```

- **П-2.2.** Машина состояний запуска:

```
 created → queued → starting → running
                                  │
        waiting_input ⇄ running   │   checkpointing → running
        (вопрос / согласование)   │
                                  ├── cancelling → cancelled
                                  └── completed | failed

 от любой контрольной точки:  fork → новый запуск (created), связь в родословной
```

- **П-2.3.** Ограничители (`max_runtime`, `max_budget_usd`, требования согласований) принимаются при создании и принудительно пресекаются платформой при нарушении.
- **П-2.4.** Создание запуска идемпотентно; повторная доставка команд безопасна.
- **П-2.5.** Управление — алгоритмическое (А-8): Run-контроллер не использует LLM; каждое его действие журналируется и воспроизводимо.

### 5.3. Журнал и поток событий

- **П-3.1.** Единая схема события: `event_id`, `event_type`, `run_id`, `agent`, `timestamp`, `seq`, `payload`.
- **П-3.2.** Журнал пополняется только добавлением; источник истины (А-3).
- **П-3.3.** Доставка: SSE-подписка фронтенда на журнал плюс дочитывание «с позиции seq»; со стороны МАС — приём потока A2A с распаковкой частей данных (3.3).
- **П-3.4.** Словарь платформенных типов: `run.status.changed`, `step.started`, `step.finished`, `tool.called`, `tool.succeeded`, `tool.failed`, `artifact.created`, `approval.requested`, `approval.resolved`, `checkpoint.created`, `checkpoint.restored`, `budget.threshold`, `log.line`. Научные события МАС — `domain.*` с произвольным содержимым: платформа хранит и показывает, но не истолковывает.

### 5.4. Артефакты

- **П-4.1.** Объектное хранилище с адресацией по содержимому; артефакт = байты + карточка: вид, тип содержимого, размер, хэш, происхождение (`run_id`, агент, шаг, входные артефакты, версии инструментов).
- **П-4.2.** Артефакты неизменяемы; новая версия — новый артефакт со ссылкой на предшественника; вместо удаления — пометка «замещён».
- **П-4.3.** Доступ наследуется от проекта; выдача — подписанными временными ссылками.

### 5.5. Трассировка

- **П-5.1.** OTel-совместимые span'ы на шаг агента, вызов модели и инструмента; связь `trace_id ↔ run_id`; сквозная трасса через MCP-шлюз и задания на кластере.
- **П-5.2.** Просмотр в Jaeger; выгрузка трассы по API.

### 5.6. MCP-контур: реестр, развёртывание, шлюз

Собственные MCP-инструменты CoScientist (разбор статей, химические утилиты, исполнители экспериментов) — самостоятельные сервисы, которые обязаны быть развёрнуты и готовы **до** старта МАС.

- **П-6.1.** Реестр MCP-пакетов: имя, версия, образ, транспорт, схема конфигурации, потребные секреты и ресурсы, проверка готовности, **класс действий** каждого инструмента (обратимое / необратимое / компенсируемое / только-для-журнала) — класс используется согласованиями (П-9.2) и откатом (6.6).
- **П-6.2.** Развёртывание по декларации: при создании запуска платформа читает `requires.tools` манифеста, находит работающие серверы подходящих версий либо разворачивает недостающие (Kubernetes), дожидается готовности каждого — и лишь затем запускает МАС. Режимы: **shared** (долгоживущий общий сервер) и **dedicated** (на время запуска, гашение по завершении).
- **П-6.3.** Маршрутизация только через шлюз: авторизация в контексте запуска, журналирование каждого вызова событиями `tool.*`, тайм-ауты, квоты, фиксация версии инструмента в каждом вызове.
- **П-6.4.** Секреты внедряются при развёртывании; в конфигурации МАС — только имена секретов.
- **П-6.5.** Проверка совместимости версий (диапазоны из манифеста) — до старта, с внятной диагностикой при отказе.
- **П-6.6.** Рекомендуемая реализация — ContextForge как реестр и шлюз плюс платформенный развёртыватель (4.6); альтернатива на этап 1 — собственный тонкий шлюз на основе `mcp_packages`.

```
Подготовка запуска:
манифест МАС ─▶ разрешение зависимостей ─▶ развёртывание/поиск ─▶ готовность ─▶ регистрация ─▶ старт МАС
 requires.tools        │                     (Kubernetes)        (healthcheck)  (ContextForge)
                       ▼
              реестр MCP-пакетов

Во время работы:
агент ─▶ MCP-шлюз ─▶ MCP-сервер
            │  авторизация · журналирование tool.* · тайм-аут · квота · версия
```

### 5.7. A2A-сторона платформы

- **П-7.1.** Платформа выступает A2A-клиентом к подключённым МАС; публикует их AgentCard (из манифеста); допускается роль A2A-сервера для внешних потребителей.
- **П-7.2.** Соответствие `run_id ↔ contextId/taskId` хранится платформой; при ветвлении новый запуск получает новую пару.
- **П-7.3.** Поддержка расширений AgentCard обязательна (объявление возможности снимков, 6.8).
- **П-7.4.** Существующий `a2a_client` Synapse — основа; доработки: повторная подписка, сверка `tasks/get`, безусловная запись входящих событий в журнал до какой-либо обработки.

### 5.8. Снимки и откат — обязательства платформы

Проектное решение — раздел 6; итоговые обязательства:

- **П-8.1.** Хранение манифестов снимков и их частей; API `restore / fork / replay`; родословная запусков (дерево ветвлений с исходной точкой каждой ветви).
- **П-8.2.** Автоматический запрос снимка на границах модулей и перед согласованиями — по политике из манифеста.
- **П-8.3.** Таймлайн контрольных точек в интерфейсе с действием «ветвиться отсюда».

### 5.9. Согласования (участие человека)

- **П-9.1.** `approval.requested` несёт контекст: что предлагается, стоимость, обратимость; решение через API/интерфейс; `approval.resolved`; продолжение — `resume_run`.
- **П-9.2.** Режимы: ручной, автоматический, пороговый (по стоимости и по классу действия из П-6.1 — необратимые действия требуют согласования).
- **П-9.3.** Перед каждым согласованием — автоснимок.
- **П-9.4.** Чат доступен и на работающем запуске: сообщения пользователя доставляются `message/send` без остановки исполнения; их обработка на ближайшей точке покоя — обязанность МАС (3.4).

### 5.10. Безопасность

- **П-10.1.** Контекст безопасности запуска (кто запустил, права, доступные секреты) передаётся адаптеру при старте и проверяется шлюзами на каждом вызове.
- **П-10.2.** Секреты — в хранилище секретов; внедрение при развёртывании; запрет значений секретов в журнале, артефактах и снимках (фильтры адаптера и шлюзов).
- **П-10.3.** Порождаемый агентами код — только в песочницах с сетевыми политиками.
- **П-10.4.** Мультиарендность — сквозной `tenant_id` (модель Synapse сохраняется).

### 5.11. Ресурсы и планирование

- **П-11.1.** Ресурсный профиль манифеста (cpu, memory, gpu: тип/число, длительность) транслируется в Kubernetes и Ray.
- **П-11.2.** Следует обеспечить очереди и квоты GPU по проектам (Kueue/Volcano), приоритеты, удержание заданий.
- **П-11.3.** Учёт потребления по запуску: CPU-часы, GPU-часы, токены.

### 5.12. Бюджеты вызовов моделей

- **П-12.1.** Все вызовы моделей — через LLM-шлюз (Bifrost): лимиты на запуск и проект, `budget.threshold`, остановка на пороге с автоснимком.

### 5.13. Фронтенд платформы

- **П-13.1.** Постановка задачи: выбор МАС из реестра, версии и профиля; ввод входа; ограничители.
- **П-13.2.** Страница запуска: лента событий из журнала (включая `domain.*`), текущий статус, вопросы `input-required` и карточки согласований с действиями.
- **П-13.3.** Таймлайн контрольных точек с метками модулей (T0–T5) и действием «ветвиться отсюда»; дерево запусков (родословная) с переходами между ветвями.
- **П-13.4.** Артефакты с происхождением и предпросмотром; трасса (переход в Jaeger).
- **П-13.5.** Служебная страница MCP: состояние серверов запусков, версии, готовность.

## 6. Снимки состояния и откат: проектное решение

### 6.1. Постановка задачи

Требуется: возвращаться к прежнему шагу исследования и идти иным путём; воспроизводить прогоны для проверки; переживать сбои без потери многочасовой работы. Стандартный A2A этого не даёт по замыслу — агент непрозрачен, наружу видны задачи, сообщения, статусы и артефакты:

```
CancelTask ≠ Откат
```

`tasks/cancel` останавливает исполнение; откат возвращает внутреннее состояние к контрольной точке и продолжает оттуда. Вторая операция базовыми средствами протокола невыразима, поэтому оформляется **отдельной возможностью самой МАС** по контракту «платформа ↔ адаптер»: A2A остаётся каналом диалога, управление снимками идёт через служебный API адаптера, а сама возможность объявляется расширением в AgentCard (6.8).

Разделение труда:

```
Платформа                                   Адаптер МАС (CoScientist)
├── хранит манифесты и части снимков        ├── знает точки покоя своей системы
├── ведёт родословную запусков              ├── исполняет барьер и сериализацию
├── таймлайн точек в интерфейсе             ├── восстанавливает состояние из снимка
├── API restore / fork / replay             └── выверяет внешние задания
└── журнал — система координат отката
```

### 6.2. Четыре уровня отката

| Уровень | Что происходит | Назначение |
|---|---|---|
| 1. Просмотр истории | Интерфейс показывает состояние на шаге N; ничего не меняется | Объяснимость, аудит |
| 2. Воспроизведение | Новый запуск от снимка либо от начала с теми же входами | Проверка, разбор происшествий (две семантики — 6.7) |
| 3. Восстановление из снимка | Состояние возвращается к точке, работа продолжается | Истинный откат; ветвление экспериментов |
| 4. Побочные действия | Внешний мир «не отматывается»: компенсирующие действия | Задания на кластере, датасеты, внешние запросы |

### 6.3. Анатомия состояния CoScientist и места контрольных точек

Состояние многоагентной системы **распределено** — его нельзя «просто сохранить» одним объектом:

```
Состояние запуска CoScientist
│
├── 1. Сеансы движка (SessionService)
│      ├── события — полная история реплик, вызовов, передач управления
│      └── словарь состояния — общие ключи дерева агентов
│          (план, отобранные гипотезы, ссылки на артефакты, счётчики)
│
├── 2. Мастер-оркестратор (структуры в памяти процесса — требуют явной выгрузки!)
│      ├── дерево подзадач и их статусы
│      ├── текущая фаза и указатель следующего шага
│      └── незакрытые вопросы и ожидающие согласования
│
├── 3. Исполнение инструментов
│      ├── граф вызовов: инструмент, вход, результат, версия
│      └── незавершённые внешние задания (обучение FEDOT, симуляции):
│          идентификаторы, параметры, статус — но не сами процессы
│
├── 4. Память (долговременная / векторная), если применяется
│
├── 5. Научное содержание: гипотезы и оценки; experiment_spec;
│      граф научного исследования; графы знаний; показатели
│
└── 6. Условия воспроизводимости: зёрна; версии моделей, промптов,
       инструментов; отпечаток контейнера; git-коммит; профиль конфигурации
```

Три следствия. **Первое:** модельные агенты между вызовами не хранят скрытого состояния — агент есть функция над историей сеанса, словарём состояния и версионированным промптом; дерево агентов, работающее в одном исполнителе, разделяет общий сеанс. Значит, восстановление сводится к обратной загрузке сеансов и явных хранилищ. **Второе:** всё, что мастер-оркестратор держит в локальных переменных и замыканиях, для снимка недоступно — отсюда дисциплина состояния (К-8). **Третье:** внешние задания входят в снимок идентификаторами и статусами, а не процессами; их судьба решается при восстановлении (6.6).

**Места контрольных точек.** Обязательные точки — границы модулей: мастер-оркестратор между передачами управления гарантированно находится в точке покоя. Типовой запуск даёт шесть меток:

```
T0 ─ задача принята, план построен
T1 ─ литературный анализ завершён
T2 ─ гипотезы сформированы и оценены
T3 ─ эксперимент спланирован (перед запуском вычислений — перед дорогим/необратимым)
T4 ─ эксперимент завершён, показатели получены
T5 ─ отчёт готов к выпуску (перед согласованием)
```

Каждый снимок — **общесистемный** (все сеансы + мастер-оркестратор + модульные хранилища), но несёт метку завершённого модуля: `label: "after_hypotheses"`. Подагенты внутри модулей отдельных точек не имеют: их промежуточное состояние после завершения модуля не нужно. Для длинного модуля экспериментов допускаются внутренние страховочные точки — те же общесистемные снимки с метками `module=experiments, step=k`. Откатывать «один модуль отдельно» нельзя и не требуется: состояния модулей связаны, единица отката — вся система на момент метки.

**Кто контролирует.** Политика точек объявлена в манифесте (`checkpoint_contract`); исполняет её мастер-оркестратор через адаптер — только МАС знает свои точки покоя. Платформа вправе запросить внеплановый снимок (адаптер исполнит на ближайшей точке покоя). Пользователь выбирает точку **отката** в интерфейсе, но не место снятия.

### 6.4. Запись состояния

#### 6.4.1. Точки покоя и барьер

Снимок допустим только в точке покоя — между зафиксированными событиями. Процедура двухфазная:

```
Платформа              Адаптер CoScientist           Мастер-оркестратор и агенты   Хранилище
   │ POST /runs/123/checkpoints │                          │                          │
   │───────────────────────────▶│ фаза 1 «остановка        │                          │
   │                            │ выдачи»: барьер          │                          │
   │                            │─────────────────────────▶│ новые шаги не раздаются; │
   │                            │                          │ текущие дорабатывают     │
   │                            │                          │ (вызов модели завершается,│
   │                            │                          │ результат ложится событием);│
   │                            │                          │ внешние задания не       │
   │                            │◀── «мир заморожен» ──────│ ожидаются — метятся      │
   │                            │ фаза 2 «сериализация»:   │ «в полёте»               │
   │                            │ обход дерева             │                          │
   │                            │ Checkpointable ─────────▶│                          │
   │                            │◀──── куски состояния ────│                          │
   │                            │ манифест, хэши           │                          │
   │                            │──────── крупные части ────────────────────────────▶│
   │                            │──────── манифест снимка ──────────────────────────▶│
   │◀─ 201: chk_002 ────────────│ снятие барьера           │                          │
   │   (checkpoint.created)     │                          │                          │
```

Бюджет барьера — секунды; самая долгая часть — дорабатывающий вызов модели, ограниченный собственным тайм-аутом. На границах модулей (T0–T5) барьер вырожден: мастер-оркестратор и так в покое.

#### 6.4.2. Интерфейс выгрузки

Каждый компонент с состоянием реализует пару методов (схематично):

```python
class Checkpointable(Protocol):
    def export_state(self) -> dict: ...   # сериализуемое представление
    def import_state(self, blob: dict) -> None: ...  # обратная загрузка
```

| Компонент | Источник | Содержимое куска | Объём |
|---|---|---|---|
| Сеансы движка | Постоянный SessionService | Словарь состояния; события — либо копией, либо ссылкой на диапазон журнала (6.4.4) | КБ–МБ |
| Мастер-оркестратор | export_state() | Дерево подзадач, фаза, указатель шага, ожидающие согласования | КБ |
| Модульные оркестраторы | export_state() | Внутренние планы модулей (если есть вне сеансов) | КБ |
| Исполнитель инструментов | export_state() | Граф вызовов, версии, задания «в полёте» | десятки КБ |
| Память | export_state() либо версионированная ссылка | Выгрузка векторного хранилища или указатель на неизменяемую версию | МБ либо ссылка |
| Научное хранилище | export_state() | Гипотезы, experiment_spec, граф исследования, графы знаний, показатели | десятки–сотни КБ |
| Конфигурация запуска | Платформа | Зёрна, версии моделей/промптов/инструментов, отпечаток контейнера, профиль | КБ |

Артефакты в снимок не копируются никогда — только идентификаторы (артефакты неизменяемы, П-4.2).

#### 6.4.3. Когда снимать

Границы модулей T0–T5 (обязательные); перед каждым согласованием (П-9.3); перед дорогими и необратимыми действиями (T3 — частный случай); по запросу платформы или пользователя; страховочно каждые N шагов внутри длинных модулей. Всё — политика `checkpoint_contract` манифеста, исполняемая адаптером.

#### 6.4.4. Экономия объёма

Куски хранятся по хэшу содержимого: неизменившиеся между соседними снимками не дублируются — инкрементальность даром. События сеансов допускается хранить ссылкой на диапазон платформенного журнала (позиции от/до), раз журнал — источник истины (А-3): тогда снимок лёгок — словари состояния, структуры оркестраторов, ссылки. Стратегия «журнал + материализованные снимки» совмещает полную историю с быстрым восстановлением.

#### 6.4.5. Чего в снимке быть не должно

Значений секретов (внедряются заново при восстановлении); открытых соединений и дескрипторов; адресов конкретных подов; больших сырых данных (их место — артефакты). Адаптер прогоняет выгрузку через фильтр очистки; приёмка — автоматический сканер секретов (6.9).

### 6.5. Хранение

Манифест снимка — компактный JSON в базе платформы; крупные части — в объектном хранилище по хэшу; целостность манифеста — собственным хэшем. Полный пример — приложение Б. Родословная запусков:

```
run_123 (профиль main)
├── chk_T1  «литературный анализ завершён»
├── chk_T2  «гипотезы сформированы»
│     ├── fork → run_124: иной план эксперимента
│     └── fork → run_125: иной набор инструментов
└── chk_T4  «эксперимент завершён»
```

Срок хранения — политика проекта; данные в покое шифруются.

### 6.6. Восстановление: как вернуть состояние в систему

#### 6.6.1. Принцип: не правка живого процесса, а порождение нового

Прямое вписывание состояния в работающую систему ненадёжно: гонки с текущими шагами, полусогласованные структуры агентов, повисшие дескрипторы, нарушенные инварианты. Поэтому восстановление всегда устроено как **создание нового экземпляра запуска**, чья инициализация идёт по пути «наполниться сохранённым состоянием» вместо «начать с нуля». Общее понятие для этой операции — **восстановление (десериализация) состояния**: свежесозданные объекты наполняются ранее выгруженными данными в единственный момент, когда инварианты гарантированно не нарушаются, — до начала работы. Исходный запуск не изменяется (А-2); `restore` отличается от `fork` лишь тем, что новая ветвь помечается для пользователя «текущей».

#### 6.6.2. Пошаговая последовательность

```
Платформа               Адаптер (новый экземпляр)         SessionService / ядро     Хранилище
   │ POST /runs/123/fork {checkpoint_id: chk_T2}                                        │
   │────────────────────▶ 1. создать запуск run_124                                     │
   │  (запись, ресурсы,    (parent_run=run_123, parent_chk=chk_T2,                      │
   │   MCP-серверы по       профиль из снимка)                                          │
   │   манифесту — как                                                                  │
   │   при обычном старте)                                                              │
   │                      2. манифест + куски по хэшам ◀───────────────────────────────│
   │                      3. проверка целостности и совместимости:                      │
   │                         schema_version; версии промптов, моделей,                  │
   │                         инструментов; профиль — режим strict / relaxed             │
   │                      4. восстановление сеансов ────▶ создать сеансы,               │
   │                         (таблица соответствия        вписать словари состояния,    │
   │                          старый id → новый id)       дописать события истории      │
   │                      5. восстановление оркестраторов ▶ import_state(): дерево      │
   │                         (мастер + модульные)          задач, фаза, указатель шага  │
   │                      6. восстановление памяти ─────▶ загрузка выгрузки             │
   │                      7. выверка внешних заданий (таблица ниже)                     │
   │                      8. контроль готовности: артефакты разрешаются,                │
   │                         инструменты нужных версий доступны, секреты внедрены       │
   │                      9. точка продолжения: цикл мастер-оркестратора                │
   │                         стартует с resume_from, а не с начала                      │
   │◀── checkpoint.restored; run_124 → running ──                                       │
   │ 10. новый taskId/contextId A2A связывается с run_124;                              │
   │     ветвь отражается в родословной                                                 │
```

**Шаг 4, восстановление сеансов.** Для каждого сеанса из снимка адаптер создаёт новый сеанс в постоянном хранилище движка, вписывает сохранённый словарь состояния и дописывает события истории (из куска либо вычитыванием диапазона журнала платформы). Идентификаторы сеансов новые; адаптер строит таблицу соответствия «старый → новый» и переписывает внутренние ссылки в плане оркестратора и графе вызовов. Поскольку движок собирает контекст модели из событий сеанса, очередной вызов любого агента после загрузки истории продолжается естественно: агент «видит» всё, что происходило до контрольной точки.

**Шаг 7, выверка внешних заданий.** Внешний мир не отматывается; для каждого задания «в полёте» на момент снимка:

| Состояние задания к моменту восстановления | Политика по умолчанию | Альтернатива |
|---|---|---|
| Успело завершиться | Результаты принадлежат старой ветви; новая видит только артефакты из `artifacts_visible`; при надобности оркестратор запустит заново | Принять результат в новую ветвь явным решением человека |
| Ещё исполняется | «Отцепить»: для новой ветви задание не запускалось | «Переподключиться» по идентификатору, если задание идемпотентно и манифест разрешает |
| Необратимое внешнее обращение | Не откатывается; остаётся в журнале старой ветви | — |

Компенсирующие действия по классам (класс инструмента — из реестра MCP-пакетов, П-6.1):

```
создано задание          → отменить задание
создан артефакт          → пометить «замещён»
создан датасет           → новая версия; старую не удалять
запущена симуляция       → остановить, если идёт; иначе пометить устаревшей
внешний запрос отправлен → не откатывается, только журналируется
```

**Шаг 9, точка продолжения.** Манифест хранит `resume_from` — метку модуля, идентификатор шага и следующее намеченное действие. Мастер-оркестратор при старте проверяет признак «восстановлен» и входит в свой цикл с этой точки: истории сеансов недостаточно, чтобы система знала, что делать дальше, — нужна именно оркестраторская отметка.

#### 6.6.3. Почему это работает

«Личность агента в моменте» полностью определяется системным промптом (версионирован), историей сеанса и словарём состояния — скрытой памяти между вызовами нет. Восстановив историю и словарь и зафиксировав промпт, получаем поведенчески эквивалентное продолжение (с поправкой на недетерминизм модели, 6.7). Всё, что в эту модель не укладывается — структуры оркестраторов, память, внешние задания, — закрывается интерфейсом Checkpointable; это и есть главная инженерная работа на стороне МАС.

#### 6.6.4. Совместимость и перенос схемы

`schema_version` в манифесте; адаптер читает текущую и две предыдущие малые версии; переход — миграционными преобразователями. Режим **strict** — любое расхождение версий промптов, моделей, инструментов или профиля запрещает восстановление (обязателен для воспроизведения); **relaxed** — расхождения журналируются предупреждениями, восстановление продолжается (по умолчанию для ветвления, где пользователь сознательно меняет условия).

### 6.7. Три режима: restore, fork, replay

**fork** — основной для научной работы: старая ветвь сохраняется, копится дерево вариантов эксперимента. **restore** — «продолжить отсюда, забыв хвост»: то же ветвление с пометкой новой ветви основной; историю не перетираем. **replay** — воспроизведение с двумя семантиками:

| Семантика | Что происходит | Детерминизм | Назначение |
|---|---|---|---|
| Строгая (по журналу) | Повторный проход с подстановкой записанных ответов моделей и инструментов; живые команды наружу не уходят | Полный | Аудит, разбор происшествий, проверка журнала |
| Свежая (от снимка) | Повторное исполнение с теми же входами и зёрнами, но живыми вызовами | Отсутствует | Проверка устойчивости научных выводов |

Семантика задаётся явно: `semantics: strict | fresh`.

### 6.8. Протокольное оформление поверх A2A

AgentCard CoScientist объявляет расширение:

```yaml
capabilities:
  streaming: true
  pushNotifications: true
  extensions:
    - uri: "https://coscientist.example/extensions/checkpoint/v1"
      description: "Снимки: создание, восстановление, ветвление, воспроизведение"
      required: false
```

Диалог — стандартным A2A. Управление снимками — служебным API адаптера (команды управления не должны зависеть от истолкования текста моделью):

```
POST /runs/{run_id}/checkpoints      создать снимок (причина, метка)
GET  /runs/{run_id}/checkpoints      перечень снимков
GET  /checkpoints/{id}               манифест снимка
POST /runs/{run_id}/restore          восстановление (checkpoint_id, режим совместимости)
POST /runs/{run_id}/fork             ветвление → идентификатор нового запуска
POST /runs/{run_id}/replay           воспроизведение (checkpoint_id, semantics)
```

Допустим дублирующий канал — A2A-сообщение со структурированной частью данных и метаданными расширения — для потребителей без служебного API; первичен API.

### 6.9. Критерии приёмки подсистемы

1. **«Золотой прогон»**: запуск доводится до T2; снимок; принудительное завершение процесса; ветвление от снимка доходит до конца; строгое воспроизведение от начала до T2 совпадает с исходным журналом бит-в-бит.
2. Снимки на T0–T5 и перед согласованиями создаются автоматически; барьер вне активного вызова модели — не более 30 секунд (типично — секунды).
3. Восстановление при расхождении версии инструмента в строгом режиме отклоняется до старта с диагностикой.
4. Сканер не находит значений секретов ни в одном куске.
5. Родословная отражает все ветвления; артефакты старой ветви, созданные после точки, новой ветви не видны.
6. Перезапуск управляющего контура платформы не теряет запуски, журнал и снимки.

### 6.10. Графы: исследование, знания, вызовы

**Граф научного исследования и графы знаний** — доменное содержимое: их строит и хранит CoScientist (научное хранилище); версия графов входит в снимок (`scientific_blob`), крупные графы оформляются версионируемыми артефактами. Тогда «состояние исследования на момент T2» — осмысленный, восстановимый объект.

**Граф вызовов агентов и инструментов** — производная наблюдаемости: платформа строит его сама из журнала (поля `agent`, события `step.*`, `tool.*`) и трасс OTel; от МАС требуется лишь честный поток событий. Дублировать построение на стороне CoScientist не нужно.

**Пригоден ли граф вызовов для откатов?** Как система координат — да: контрольные точки ложатся на его узлы, таймлайн и строгое воспроизведение идут ровно по журналу. Как механизм восстановления — нет: «проиграть граф заново» живыми вызовами недетерминировано (модели) и дорого (эксперименты), а записанных ответов хватает лишь для строгого воспроизведения, но не для продолжения работы вперёд. Поэтому роли разделены: журнал и граф — навигация, аудит, строгое воспроизведение; материализованные снимки — восстановление и ветвление.

## 8. План работ по этапам

### Этап 0. «Контракты и сквозной пилот» (~3 недели)

| Сторона | Результаты |
|---|---|
| Платформа | Схемы манифеста, событий и снимков (документы + JSON Schema) в общем репозитории контрактов; Run-контроллер v0 (создать / статус / отменить); приём потока A2A; реестр с ручной регистрацией |
| CoScientist | manifest.yaml с профилями; тонкий адаптер (start / status / cancel + поток событий); сквозные идентификаторы |

**Приёмка:** CoScientist запускается через платформу; события в ленте; отмена срабатывает. **Риск:** расползание схем — общий репозиторий контрактов с первого дня.

### Этап 1. «События, артефакты, инструменты» (~5 недель)

| Сторона | Результаты |
|---|---|
| Платформа | Журнал с дочитыванием по `seq`; хранилище артефактов с происхождением; MCP-контур: развёртыватель + шлюз (ContextForge либо собственный тонкий — решение закрепляется здесь); предварительное развёртывание MCP-серверов по манифесту; сквозная трассировка |
| CoScientist | Все инструменты через шлюз; артефакты через платформу; experiment_spec v1; полный словарь событий |

**Приёмка:** полный научный сценарий (гипотезы → план → эксперимент → отчёт) через платформу; по журналу — ни одного вызова мимо шлюза; MCP-серверы подняты платформой до старта и прошли готовность.

### Этап 2. «Снимки, откат, участие человека» (~6 недель)

| Сторона | Результаты |
|---|---|
| Платформа | Хранилище снимков; API restore / fork / replay; родословная; таймлайн точек во фронтенде с «ветвиться отсюда»; согласования с автоснимком |
| CoScientist | Постоянные сеансы; Checkpointable у оркестраторов и хранилищ; барьер; восстановление по 6.6.2; метки T0–T5; фильтр секретов |

**Приёмка:** все шесть критериев 6.9, включая «золотой прогон».

### Этап 3. «Ресурсы, квоты, закалка» (~6–8 недель)

| Сторона | Результаты |
|---|---|
| Платформа | Очереди и квоты GPU (Kueue либо Volcano — по испытаниям); учёт потребления; бюджеты моделей с порогами и автоснимком; мультиарендные политики; решение по Temporal; нагрузочные и отказоустойчивые испытания |
| CoScientist | Ресурсные профили; длительные эксперименты через очередь; участие в испытаниях |

**Приёмка:** два арендатора одновременно с честным разделением GPU; перезапуск управляющего контура без потери запусков, журнала и снимков.

| Этап | Срок | Ключевая веха |
|---|---|---|
| 0 | ~3 нед. | Первый запуск CoScientist через платформу |
| 1 | ~5 нед. | Полный научный сценарий; инструменты и артефакты под учётом |
| 2 | ~6 нед. | «Золотой прогон»: снимок → падение → ветвление → завершение |
| 3 | ~6–8 нед. | Промышленная эксплуатация на кластерах института |

## 9. Риски и меры противодействия

| Риск | Последствие | Мера |
|---|---|---|
| Платформа продолжит развиваться по модели «агенты живут внутри», контрактный слой не появится | Каждую внешнюю МАС придётся переписывать под движок платформы | Contract-first этапом 0; настоящее ТЗ — предмет письменной договорённости; пилот этапа 0 как доказательство модели |
| Соблазн выставить каждого внутреннего агента отдельным A2A-сервисом | N машин состояний, рассинхронизация контекста, хрупкость | Гранулярность «одна МАС — один сервис» (3.1); модульность — метками точек и полем agent в событиях |
| Управление запусками через LLM-агент платформы | Недетерминизм в контуре управления, невоспроизводимость | А-8: Run-контроллер алгоритмический; агенты Synapse — только для её собственных сценариев |
| Недетерминизм моделей обесценивает воспроизведение | «Повторил — получил другое» | Две семантики replay (6.7); строгая — только по журналу с записанными ответами |
| Разрастание объёма снимков | Дорогое хранение, медленный барьер | Адресация по содержимому; события — ссылками на журнал; артефакты — идентификаторами |
| Несовместимость версий снимков | Старые снимки нечитаемы | schema_version + миграционные преобразователи + поддержка двух предыдущих малых версий |
| Двойное владение MCP-серверами | «Ничьи» сервисы, рассинхрон версий | Реестр пакетов: разработка — МАС, эксплуатация — платформа; диапазоны версий в манифесте, проверка до старта |
| Дефицит GPU | Простои, конфликты команд | Квоты и приоритеты этапа 3; бюджеты времени в профиле; удержание в очереди вместо отказов |
| Молодость расширений A2A | Изменения спецификации ломают интеграцию | Служебный API первичен; расширение — тонкая, дёшево заменяемая обёртка |
| Самописный управляющий контур без боевой обкатки | Скрытые дефекты под нагрузкой | Пилот этапа 0 на реальном сценарии; нагрузочные этапа 3; журнал-истина упрощает разбор происшествий |
| Осиротевшие внешние задания при откате | Двойной расход GPU | Политики выверки (6.6.2, шаг 7); все задания через шлюз (А-5) — платформа знает, что отменять |

## Приложение В. Интерфейс подключаемой МАС (реализует адаптер)

**A2A (диалог и жизненный цикл задач):**

```
AgentCard                     — публикация возможностей (порождается реестром из манифеста)
message/send                  — входная задача; ответы на вопросы; решения согласований
message/stream                — поток событий (статусы, артефакты, части данных со словарём П-3.4)
tasks/get                     — сверка состояния задачи
tasks/cancel                  — остановка
tasks/resubscribe             — повторная подписка после обрыва
```
