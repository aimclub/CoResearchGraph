# Контекстный граф исследования — спецификация для реализации

## 0. Контекст и цель

Мы разрабатываем МАС (мультиагентную систему) для научно-исследовательского процесса.
Состав агентов: **оркестратор**, **ресечер**, **кодер**, + ещё несколько (валидатор/критик,
возможно агент формализации вопроса, агент инициализации контекста).

Проблема, которую решает граф: агенты не должны обмениваться состоянием через передачу
всей истории диалога друг другу. Вместо этого вводится **общее персистентное состояние —
граф исследования**, к которому агенты обращаются как к blackboard: пишут узлы своих типов,
читают релевантные подграфы, а оркестратор читает граф целиком и решает, кого запускать дальше.

Граф — это не лог сообщений и не файловая база знаний, а **типизированный property graph**:
узлы имеют тип, атрибуты, статус, источник и временную метку; рёбра типизированы и направлены.
Один граф = одно исследование (один корневой вопрос). Граф растёт по мере работы, ветвится,
может содержать тупиковые (опровергнутые) ветки — они не удаляются.

Задача этого документа — зафиксировать: какие типы узлов и рёбер существуют, кто их создаёт,
кто как читает, как граф эволюционирует по фазам, и какие технические требования к реализации.

## 1. Модель данных

### 1.1 Узел (Node)

Каждый узел имеет обязательные поля:

```
{
  id: string,
  type: string,          // один из типов ниже, например "Hypothesis"
  attrs: { ... },         // атрибуты, специфичные для типа
  status: string,         // допустимые значения зависят от типа (см. 1.3)
  source: string,         // какой агент/человек создал узел
  created_at: timestamp,
  updated_at: timestamp
}
```

### 1.2 Ребро (Edge)

```
{
  id: string,
  type: string,          // "мотивирует", "проверяется_через" и т.д.
  from: node_id,
  to: node_id,
  attrs: { ... }          // опционально, например вес/уверенность
}
```

### 1.3 Типы узлов

**Слой 1 — эпистемические объекты**

| Тип | Атрибуты | Статусы |
|---|---|---|
| `ResearchQuestion` | формулировка, предметная область, специфичность, gap, декомпозиция, целевая_постановка, форма_исследования, УГТ | открыт / декомпозирован / закрыт |
| `Hypothesis` | формулировка, обоснование, приоритет | сформулирована / на_проверке / подтверждена / опровергнута / отложена |
| `Evidence` | подтип (литературное / экспериментальное / вычислительное / экспертное / мета), содержание, вес/надёжность | получено / валидировано / отвергнуто |
| `Conclusion` | синтез, ссылки на свидетельства, новый_вопрос (опционально) | черновик / утверждено |

**Слой 2 — методологический каркас**

| Тип | Атрибуты | Статусы |
|---|---|---|
| `VerificationMethod` | тип метода, входы, выходы, стоимость, ограничения | запланирован / выполняется / выполнен / провален |
| `ConfirmationCriteria` | порог, число_подтверждений, требование_воспроизводимости | не_выполнены / выполнены |

**Слой 3 — контекст реализуемости**

| Тип | Атрибуты | Статусы |
|---|---|---|
| `Tool` | название, тип, требования | доступен / нужна_адаптация / создаётся / не_удалось_создать |
| `Resource` | тип (GPU-часы, токены, реагенты, время, часы_экспертов), остаток, лимит | доступен / исчерпан |
| `EmpiricalBase` | тип (датасет / корпус / свод_знаний), объём, источник | — |
| `Constraint` | подтип (профиль_исследования, методологические_нормы, теоретические_рамки, доменные_стандарты, этика/регуляторика, экспертное_знание, роли) | активен |

**Слой 4 — артефакты**

| Тип | Атрибуты |
|---|---|
| `CodeArtifact` | репозиторий/путь, версия, описание |
| `GeneratedData` | путь, схема, объём |
| `Report`, `Publication`, `Spec` (ТЗ), `EfficiencyJustification` | текстовое содержимое/ссылка |

**Слой 5 — логика навигации** (в основном используется оркестратором, не обязательно материализуется как узлы, но статусы/переходы должны логироваться)

- `TransitionTrigger` — условие перехода (может быть правилом оркестратора, не узлом)
- `InformationalDependency` — частичный порядок (выражается через рёбра `требует`/`порождает`)
- `CompletionCriteria` — исчерпывающий / прагматичный / ресурсный / экономический
- `AIApplicationModel` — уровень: лаборант / ассистент / копайлот / архитектор

**Слой 6 — экономика**

| Тип | Атрибуты |
|---|---|
| `CostModel` | формула/правило расчёта стоимости шага |
| `EfficiencyMetric` | время, стоимость, качество |

### 1.4 Типы рёбер

| Ребро | От → К | Смысл |
|---|---|---|
| `мотивирует` | Question → Hypothesis | вопрос порождает гипотезу |
| `проверяется_через` | Hypothesis → VerificationMethod | какой метод проверяет гипотезу |
| `требует` | Hypothesis → Tool | нужен инструмент |
| `использует` / `потребляет` | VerificationMethod → Tool / Resource | метод использует ресурс/инструмент |
| `порождает` | VerificationMethod → Evidence; Conclusion → ResearchQuestion (новый) | создание нового узла |
| `поддерживает` / `опровергает` / `уточняет` | Evidence → Hypothesis | как свидетельство влияет на гипотезу |
| `основано_на` | Conclusion → Evidence (множество) | синтез |
| `определяет_достаточность` | ConfirmationCriteria → Conclusion | критерий для вывода |
| `регулирует` | Constraint → VerificationMethod / ConfirmationCriteria | нормы ограничивают метод |
| `ограничивает` | Constraint → Hypothesis / VerificationMethod | этика/теория ограничивают |
| `формируется_из` | Artifact ← Conclusion / Evidence | артефакт строится из данных |
| `контекстуализирует` | Constraint(профиль) → ResearchQuestion | рамка интерпретации вопроса |
| `определяет_область` | ResearchQuestion → EmpiricalBase | какие данные релевантны |
| `относится_к` | Evidence → ResearchQuestion / Hypothesis | привязка свидетельства |

## 2. Права записи по агентам

Каждый агент пишет **только узлы разрешённых для него типов**. Это должно быть
зафиксировано как схема-валидация (см. раздел 5) — попытка записать неразрешённый тип/статус
отклоняется на уровне API графа, не долетая до общего состояния.

| Агент | Создаёт узлы | Меняет статусы | Создаёт рёбра |
|---|---|---|---|
| **Агент инициализации** (может быть частью оркестратора) | `ResearchQuestion` (корень), `Tool`, `Resource`, `EmpiricalBase`, `Constraint` (профиль) | — | `контекстуализирует`, `определяет_область` |
| **Оркестратор** | служебные узлы задач (если нужны) | статусы гипотез (сформулирована→на_проверке), списание `Resource` | — (в основном читает) |
| **Ресечер** | `Evidence` (литературное, мета), обогащает `EmpiricalBase`; опционально `Hypothesis` если нет отдельного генератора гипотез | `Evidence.status` | `относится_к`, `поддерживает`/`опровергает`/`уточняет` |
| **Кодер** | `Tool`, `CodeArtifact`, `GeneratedData`, `Evidence` (вычислительное) | `Tool.status` (создаётся→доступен/не_удалось_создать) | `использует`, `потребляет`, `порождает` |
| **Валидатор/критик** | `Conclusion` | `Hypothesis.status` → подтверждена/опровергнута/отложена | `основано_на`, `определяет_достаточность` |
| **Человек в контуре** | `Constraint` (экспертное знание), утверждает черновики | `Conclusion.status` черновик→утверждено, утверждение профиля/списка гипотез | — |

Если в вашей текущей МАС агентов меньше (например нет отдельного валидатора) — соответствующие
обязанности временно берёт на себя оркестратор или ресечер/кодер, но типы узлов и статусы
не меняются — просто сужается число "писателей".

## 3. Как агенты читают граф

- **Оркестратор** читает граф целиком, но не углубляется в содержимое атрибутов — его логика
  работает на уровне *статусов и наличия рёбер* (то есть, по сути, это запросы к графу):
  - "есть Hypothesis.status == сформулирована, у которой все связанные Tool.status == доступен?" → запустить проверку
  - "появилось Evidence с ребром опровергает?" → пересмотр ветки
  - "путь Hypothesis → Evidence → ConfirmationCriteria замкнут?" → запустить валидатора
  - "Resource.остаток < стоимость следующего шага?" → сигнал к завершению/эскалации

- **Рабочие агенты** (ресечер, кодер и т.п.) не должны получать весь граф — им передаётся
  **контекстный срез**: целевой узел + обход на 1–2 ребра. Например, для кодера, запускаемого
  на гипотезе H3: сама гипотеза, связанный `VerificationMethod`, требуемые `Tool` со статусами,
  `ConfirmationCriteria` (что логировать), релевантная `EmpiricalBase`, применимые `Constraint`.

  Практическая рекомендация: реализовать функцию `get_context_slice(node_id, depth=1|2)`,
  которая возвращает поднграф — и именно её выход, а не весь граф, подставлять в промпт агента.

## 4. Жизненный цикл графа (фазы роста)

1. **Инициализация** — создаётся корневой `ResearchQuestion` + звезда контекста
   (`Tool`, `Resource`, `EmpiricalBase`, `Constraint`/профиль). Профиль утверждается человеком.
2. **Разведка** — ресечер создаёт куст `Evidence` (литературных + мета) вокруг вопроса,
   обогащает `EmpiricalBase`.
3. **Ветвление** — генерируются несколько `Hypothesis` параллельными ветками от вопроса,
   каждая связывается с `VerificationMethod`, `Tool`, `ConfirmationCriteria`. Часть гипотез
   может сразу уйти в статус "отложена" (нет инструментов). Человек утверждает приоритизацию.
4. **Углубление** — для гипотезы в работе: если нужного `Tool` нет — кодер сначала создаёт его
   (статус создаётся → доступен/не_удалось_создать), затем выполняется `VerificationMethod`,
   порождаются `Evidence` (вычислительные), списываются `Resource`.
5. **Свёртка** — как только путь Hypothesis → Evidence → ConfirmationCriteria замкнут,
   валидатор создаёт `Conclusion`. Conclusion может породить новый `ResearchQuestion` — граф
   получает новый корень, цикл повторяется.
6. **Кодификация** — по срабатыванию `CompletionCriteria` создаются артефакты (`Report`,
   `Publication`, `Spec`), которые ссылаются `формируется_из` на `Conclusion`/`Evidence`.
   Считается `EfficiencyMetric` по всему графу.

Важно: **ветки растут параллельно и независимо** — несколько гипотез могут одновременно
находиться в разных фазах. Опровергнутые ветки **не удаляются** — остаются как отрицательный
результат и как контекст, чтобы не повторять уже проверенные гипотезы.

## 5. Технические требования к реализации

1. **Хранилище**: для прототипа — NetworkX (Python) с сериализацией в JSON;
   для продакшена — property graph store (Neo4j или аналог), где триггеры оркестратора
   превращаются в запросы (Cypher), а контекстный срез — в обход `MATCH (n)-[*1..2]-(m)`.
2. **Схема-валидация**: перед принятием записи от агента — проверка, что (а) тип узла
   разрешён для данного агента, (b) переход статуса допустим (нельзя из "опровергнута" сразу
   в "подтверждена", например), (c) рёбра связывают допустимые пары типов. Валидация должна
   ловить это до того, как запись попадёт в общий граф — это первый барьер против галлюцинаций
   LLM-агентов.
3. **Транзакционность записи**: агент коммитит результат шага целиком (все новые узлы + рёбра +
   смена статусов) одной операцией — оркестратор не должен видеть промежуточное/половинчатое
   состояние.
4. **Блокировка веток**: при переводе `Hypothesis.status` в "на_проверке" — эта ветка считается
   занятой, чтобы два агента не начали параллельно работать над одной и той же гипотезой.
5. **Источник и трассировка**: каждый узел хранит `source` (какой агент/человек создал) —
   это даёт прямую трассировку "вопрос → артефакт" по рёбрам в обратную сторону для составления
   отчётов, и явно показывает долю автоматизации vs участия человека.
6. **API графа** (минимальный набор функций, которые нужно реализовать):
   - `create_node(type, attrs, source)`
   - `create_edge(type, from_id, to_id)`
   - `update_status(node_id, new_status)` — с проверкой допустимости перехода
   - `get_context_slice(node_id, depth)` — для передачи агентам
   - `query(pattern)` — для триггеров оркестратора (набор именованных запросов, см. раздел 3)
   - `get_provenance(node_id)` — обратная трассировка до корневого вопроса

## 6. Что нужно от агента-реализатора

- Реализовать модель данных (раздел 1) и API графа (раздел 5.6) поверх выбранного хранилища.
- Встроить схема-валидацию прав записи (раздел 2) — по одному writer-интерфейсу на каждого
  агента, ограниченному его разрешёнными типами/статусами.
- Реализовать `get_context_slice` и подключить её как единственный способ, которым рабочие
  агенты получают контекст из графа (вместо передачи истории диалога).
- Реализовать в оркестраторе набор именованных запросов-триггеров из раздела 3 и связать их
  с текущей логикой выбора следующего агента.
- Не реализовывать удаление узлов — отложенные/опровергнутые ветки остаются в графе.
- Свериться с текущим кодом МАС: если каких-то агентов из таблицы раздела 2 в системе ещё нет,
  временно объединить их обязанности с ближайшим существующим агентом, сохранив типы узлов
  и переходы статусов без изменений.
