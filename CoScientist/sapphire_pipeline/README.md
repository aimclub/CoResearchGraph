```bash
# Запуск из корня проекта
cp CoScientist/sapphire_pipeline/config.env.example config.env
python CoScientist/sapphire_pipeline/__main__.py --page-size 100 --max-articles 2000
```

1. Устанавливается блокировка от одновременного запуска, загружаются настройки из `config.env` и создаются клиенты S3, Chroma, LLM и embeddings.
2. Открывается локальный SQLite-реестр `data/sapphire_registry.sqlite3`. Для каждой записи в нём сохраняются идентификаторы, название, исходный JSON, статус, число попыток, последняя ошибка и время обновления. Путь можно изменить через `--registry-file`.
3. При запуске открывается коллекция Chroma без чтения всех чанков. Для новой публикации выполняется точечный запрос по DOI. Проверяются также распространённые старые формы DOI с префиксом `doi.org` и верхним регистром. Найденные дубли запоминаются на время прохода.
4. Из Sapphire поочерёдно читаются страницы двух серверных фильтров: `domain=ai&domain_score=1e-12` и `domain=chembio&domain_score=1e-12`. Записи, попавшие в оба результата, объединяются. В Sapphire нет query-параметра для open access, поэтому `is_open_access` проверяется после получения записи.
5. Публикация добавляется в реестр. Статусы `ingested`, `already_in_rag`, `domain_filtered`, `not_open_access`, `missing_openalex_id` и `no_usable_pdf` считаются завершёнными и при следующем запуске сразу пропускаются. `failed` и оставшийся после прерывания `processing` обрабатываются повторно. Реестровые пропуски не расходуют `--max-articles`, поэтому следующий запуск проходит дальше уже известных записей.
6. Проверяются оценки `domains`: требуется `score > 0` у `ai` или `chembio`, при этом положительная оценка `photonics` исключает статью, даже если есть AI/chembio. Нулевые оценки не считаются принадлежностью к теме. Без подходящих оценок статья пропускается с причиной `domain_filtered`; такие пропуски входят в `--max-articles`.
7. DOI статьи нормализуется и проверяется по существующим чанкам. Если статья уже есть в RAG, она пропускается.
8. Проверяется `is_open_access`. Если значение не равно `true`, статья пропускается.
9. Проверяется наличие корректного `openalex_id`. Если его нет, статья пропускается; иначе запрашивается `GET /crawler/openalex/works/{openalex_id}`.
10. Из ответа извлекаются предварительные `domain` и `field`. Если классификация отсутствует, фиксируется ошибка статьи. Если DOI ещё не известен, он берётся из ответа и повторно проверяется на дубли.
11. Сначала PDF запрашивается через `GET {PDF_CRAWLER_URL}/api/v1/download?url=https://doi.org/{doi}` (или по `publication.dblp_url`, если DOI отсутствует). Если crawler вернул ошибку, некорректный PDF или для него нет DOI/DBLP, выполняется прямое скачивание по ссылкам, полученным с помощью `GET /crawler/openalex/works/{openalex_id}`, в порядке: `publication.pdf_url`, `work.content_urls.pdf`, `best_oa_location.pdf_url`, `primary_location.pdf_url`, затем открытые `locations[].pdf_url`. Повторяющиеся ссылки удаляются; после первого успешного скачивания перебор прекращается. Для HTTPS-запросов к `api.openalex.org` и `content.openalex.org` добавляются email и API-ключ из `OpenAlexSettings`; Basic Auth crawler туда не передаётся. Для обоих способов проверяются размер и сигнатура PDF. Если все способы не сработали, сетевые ошибки, ошибки авторизации и временные HTTP-ошибки оставляют статью в `failed` для повторной попытки; при отсутствии пригодных PDF без таких ошибок выставляется `no_usable_pdf`. Ошибка crawler не препятствует успешной загрузке через запасную ссылку.
12. PDF скачивается в память, вычисляется `article_id = MD5(pdf)`. Если такой идентификатор уже есть в Chroma, статья пропускается.
13. PDF сохраняется в `S3_PUBLIC_BUCKET` по ключу `articles/{domain}/{article_id}/paper.pdf`.
14. Запускается обработка через оригинальные этапы `papers_processing_refactoring`. Используются сохранённые состояния этапов для возобновления незавершённой обработки.
15. Итоговый статус записывается в SQLite. При ошибке сохраняются `failed`, текст ошибки и число попыток; ошибка отдельной статьи не останавливает остальные. Ошибка чтения страницы Sapphire прерывает проход.
16. Обработка завершается при пустой странице или достижении `--max-articles`. Лимит учитывает новые и повторно обрабатываемые записи, включая впервые определённые пропуски и ошибки; готовые записи из реестра лимит не расходуют. Без `--max-articles` читаются все страницы. Выводятся количество просмотренных и загруженных статей, причины пропусков и число ошибок.
