# Надёжное согласование плана эксперимента после исчерпания критики

Дата: 26.09.2026. Проверенная ветка: `dev_1`, HEAD `54b65e83` с уже существующими локальными изменениями.

Статус на 26.09.2026: этапы 1–6 реализованы и покрыты unit-тестами. Validation diagnostics приведены к JSON-native контракту; durable session append/create/replace получили предварительную проверку и откат; checkpoint больше не маскирует неизвестные типы через `fallback=str`; последний исполнимый кандидат после исчерпания автоматических доработок передаётся человеку; технические блокеры не обходятся подтверждением; у dedicated reviewer удалены дублирующие generic approval tools; UI и машинный outcome различают ожидание, блокировку, отказ и завершение. Для exhausted-review добавлены детерминированная идентичность карточки и объединение одновременных повторов в один запрос.

Этап 7 выполнен частично: reconnect и одновременный повтор используют один pending-запрос, а одинаковый durable review получает тот же transport id после перезапуска. Автоматическое продолжение coroutine после полного рестарта процесса не реализовано: для него всё ещё нужен отдельный resume-handler, который загрузит checkpoint и возобновит stage без повторного LLM-планирования. Поэтому текущая реализация не должна обещать автоматический resume процесса после рестарта. Рабочая сессия из инцидента автоматически не изменялась и не перезапускалась.

## 1. Целевое поведение

Когда автоматические доработки исчерпаны, система прекращает переписывать план и передаёт текущую версию пользователю. Пользователь видит сам план, оставшиеся замечания и последствия их принятия. После явного подтверждения запускается именно показанная версия.

«Принять текущий план» означает выбрать его для согласования, а не молча утвердить запуск. Недостатки полноты и методики могут быть приняты человеком; технически невалидный план, отсутствующие полномочия или недоступный исполнитель не становятся исполнимыми от нажатия кнопки.

Обычная работа режима `auto` сохраняется. Исключение — согласование после исчерпания критики: здесь требуется реальный ответ человека, как запрошено пользователем. Глобальный режим других сессий не переключается.

3. `experiments/review.py::_review_plan()` помещает errors в `experiment_plan_validation_errors` без нормализации. Аналогичный путь есть после выбора маршрута.
4. `_publish_state()` переносит это значение в `Event.actions.state_delta`. Безопасный `default=str` используется только для лога и не меняет исходные данные.
5. Даже если следующая версия прошла схему, старые ошибки не очищаются до полного одобрения критикой. Они могут пережить несколько ревизий и попасть в итоговое событие.

7. Следующие сообщения повторно сериализуют ту же историю и снова падают. Очистить только текущий state недостаточно, если проблемный объект уже находится в историческом `state_delta`.

Исчерпание критики не создаёт `ValueError`: оно обнаружило отдельный дефект обработки диагностик при выходе из модуля.

## 3. Не смешивать разные бюджеты

| Ограничение | Текущий смысл | Что менять |
| --- | --- | --- |
| `max_plan_revisions`, default 4 | Последовательные отказы схемы/детерминированной критики | После исчерпания — финальное human-review вместо отказа без карточки |
| `max_inventory_blocker_hits`, 2 | Повтор отсутствующих инструментов | Та же финальная развилка; неизвестный инструмент не разрешать одним approval |
| `critic_max_rounds` | Доработки по замечаниям LLM-критика `SessionAgent` | Последняя версия передаётся дальше уже сейчас; при неразрешённой критике зафиксировать exhausted и направить на human-review без нового автоматического цикла |
| `max_replan_rounds` | Новый план после оценки результатов исполнения | Не увеличивать и не расходовать на повторную доставку HITL |
| Внешний бюджет вызовов ExperimentModule | Повторные делегации оркестратора | Ожидание/возобновление согласования не должно запускать модуль заново или сбрасывать исчерпанную критику |

Сохранить ограниченный общий бюджет автоматических доработок одного раунда; отдельно учитывать причины расхода для диагностики. Не вводить независимые автоматически сбрасываемые счётчики, которые вместе создадут бесконечный цикл. Успешная схема очищает schema errors, но сама по себе не обнуляет общий бюджет отказов критики.

## 4. Предлагаемый маршрут

```text
Кандидат плана → проверка схемы и исполнимости → детерминированная критика
  ├─ всё принято → существующий путь HITL/auto → исполнение
  ├─ нужны изменения и бюджет остался → ограниченная доработка
  └─ автоматические доработки исчерпаны
       ├─ текущий кандидат исполним → согласование с замечаниями
       └─ кандидат неисполняем → показать проект и блокеры, запуск недоступен

Финальное согласование
  ├─ пользователь подтверждает → повторная проверка версии/исполнимости → исполнение
  ├─ пользователь отклоняет → остановлено пользователем
  ├─ запрашивает доработку → новый явно запрошенный ограниченный раунд
  └─ нет ответа → ожидание/пауза, без запуска и без нового планирования
```

### 4.1. Хранить кандидат до окончательного одобрения

Сейчас `initialize_runtime()` вызывается только после успешной критики. Схемно-валидный, но отклонённый критикой кандидат не имеет отдельного надёжного snapshot.

Добавить один версионированный review-state с JSON-совместимыми значениями, например `experiment_plan_review`. Поля: `status`, `run_id`, `plan_id`, `revision`, `digest`, `candidate`, `critique`, `schema_errors`, `execution_blockers`, `rounds_used`, `exhaustion_reason`, `review_id`, `decision`.

- Не использовать исполняемый runtime как хранилище неутверждённого проекта.
- Сохранять текущий схемно-валидный кандидат до ветки `critique.verdict != approve`.
- Невалидный новый ответ хранить отдельно как ограниченный диагностический draft; не выдавать его за предыдущую валидную версию.
- Идентичность привязать к текущему исследованию/run и версии контекста, а не только к `plan_id`. Digest считать по нормализованному плану; изменение плана после показа требует нового согласования.
- Приоритет — текущий план, как просил пользователь. Не выбирать незаметно «лучший» по числу замечаний.
- Если текущая версия невалидна, но сохранилась предыдущая исполнимая версия того же run, можно предложить её как явно обозначенный отдельный выбор. Самостоятельного отката нет.
- В первом этапе достаточно текущего кандидата и последнего валидного snapshot; полная история всех больших JSON не обязательна.

Новые поля включить в публикацию через AgentTool, очистку действительно нового run и логику resume. Старые флаги `experiment_plan_review_paused` и pause reason временно поддерживать как производные для совместимости; не создавать несколько независимых источников статуса.

### 4.2. Разделить замечания и запреты исполнения

Текущих `minor/major/blocker` недостаточно: например, `Direct MCP-to-Coder mode is disabled` имеет severity `major`, но это не пожелание к качеству.

Добавить стабильный код правила и явную политику разрешения (`advisory`, `human_override`, `non_overridable` или эквивалент). Не классифицировать по поиску подстрок в английском `message`. Для неизвестного правила override по умолчанию запрещён.

| Пример | Финальное согласование |
| --- | --- |
| Нет OP-3/OP-6, неполное покрытие методики | Человек может согласовать частичный объём; карточка и отчёт сохраняют список непокрытых требований |
| Много задач, необязательная визуализация, minor замечания | Предупреждение; обычный путь не усложняется |
| Ошибочный JSON, неизвестный producer, цикл зависимостей | Запуск запрещён до исправления структуры |
| Выключенный маршрут, запрещённый MCP→Coder, отсутствующий обязательный tool/agent | Запуск запрещён до исправления маршрута/окружения; approval не меняет разрешения |
| Нарушение зафиксированного пользователем scope, неподтверждённые/фиктивные ссылки | Не обходить обычной кнопкой «согласовать замечания»; требуется отдельное исправление/явное изменение задания |

Проверку исполнимости переиспользовать между review и `start_task`, без двух расходящихся наборов правил. Не запускать эксперименты или сборку инструментов в таком preflight. Статическая готовность не гарантирует доступность сети в будущем — ошибки реального запуска по-прежнему обрабатываются штатным runtime.

Не менять `PlanCritique.verdict` на `approve` искусственно. Исходная критика остаётся фактом. Разрешение на запуск хранить отдельно как решение человека: версия/digest, принятые коды замечаний, время и источник решения. В `approve_plan()` предусмотреть узкую проверяемую ветку такого разрешения; простой `force=True` недопустим. Решение не может создаваться произвольным текстом LLM или подменой её state.

При согласованном неполном покрытии отчёт не должен утверждать, что исходное ТЗ выполнено полностью или все гипотезы проверены.

### 4.3. Один владелец согласования

У `ExperimentPlannerAgent` в YAML нет явного `request_approval`, но `assembly/assembler.py::_build_custom_agent()` автоматически добавляет HITL tools при `hitl: true`. Транскрипт подтверждает, что обе общие карточки вызвал сам планировщик.

Разделить две возможности: внутренний review-loop и LLM-доступ к общим HITL tools. Для dedicated experiment-review агентов не добавлять повторное общее согласование плана. Не отключать `hitl: true` целиком: это может убрать нужный handler/внутренний review.

Единственный владелец plan approval — детерминированный review-контроллер после проверки кандидата. У других агентов сохраняются нужные запросы входных данных и согласования иных действий. Выбор маршрута может быть отдельным содержательным вопросом, но не повторным утверждением того же плана.

### 4.4. Обязательный человек при fallback

В `HITLRequest` добавить типизированную политику, например `requires_human`. Она должна учитываться и в fast-path `_auto_approve()`, и в Web/Console/A2A обработчиках: отказ от fast-path без изменения handler недостаточен.

- `decision_source=mode_auto` не принимается для exhausted-review.
- Для `auto` этот запрос получает отдельное ненулевое окно ожидания либо устойчивое pending-состояние; timeout не может означать approval.
- При отсутствии интерфейса вернуть явное ожидание человека/паузу, а не бесконечно держать модельный вызов и не выполнять план.
- Кнопка «Доработать» не запускает скрытый бесконечный цикл. Только явное действие пользователя открывает новый ограниченный раунд; прошлый расход и решение остаются в истории.
- Новое глобальное обязательное согласование для нормального auto-пути не вводится.

### 4.5. Понятный результат на границе модуля

Модуль последовательный; ResultReview всё равно получает управление после остановленного планирования и выдаёт общую фразу про reporting. Она маскирует исходную причину при возврате через AgentTool.

Добавить машинный outcome (`awaiting_human`, `blocked`, `rejected`, `completed`, `failed`) с `stage`, `reason`, `run_id`, `review_id` и ссылкой на review-state. Сформировать его на границе ExperimentModule из состояния, а не из текста последнего агента.

ResultReview не должен заменять остановку планирования своим общим сообщением. Оркестратор и report guard при `awaiting_human` не запускают заново planner/executor и не сочиняют итоговый научный отчёт. Текст пользователю: «Лимит автоматических доработок исчерпан. План готов к согласованию; эксперимент ещё не запускался» либо конкретный список технических блокеров.

## 5. Безопасное состояние и сохранение

### 5.1. Нормализация диагностик на источнике — P0

Ввести единый преобразователь validation errors в ограниченный JSON-native diagnostic contract: `code/type`, `loc`, `message`, безопасный контекст при необходимости. Не сохранять exception objects, traceback или большие исходные `input` без необходимости. Сообщения также ограничивать и очищать от секретов.

Использовать одинаковый путь для первичной валидации, проверки выбранного маршрута и контекстных инвариантов. Простой вариант для Pydantic — исключить `context/input` из `errors()` либо получить JSON-представление и выделить необходимые поля; конкретный вариант закрепить репродукцией на установленной версии.

После успешного schema-validation сразу очищать ошибки предыдущей версии, даже если новая критика требует revision. Передавать в `revision_feedback` только диагностику соответствующего кандидата.

Нельзя лечить проблему глобальным `json.dumps(default=str)` или безусловной строкификацией всего session state: это скроет неправильные типы научных результатов и артефактов.

### 5.2. Атомарность append — P0/P1

Перед ADK-мутацией строго проверять сериализуемость projected session/event. Отказ должен содержать путь проблемного поля и его тип без полного содержимого пользовательских данных. Некорректное событие не добавляется, последующее корректное сообщение должно сохраняться.

Для ошибки записи после предварительной проверки предусмотреть согласованный откат/транзакционную публикацию. Проверить не только canonical session, но и переданную ADK-копию, `events`, timestamps, затронутые app/user state: установленный ADK меняет эти объекты тоже. Поверхностного копирования dict для вложенных значений недостаточно.

Сериализовать операции соответствующими async-locks. Не удерживать `threading.RLock` через `await`. Для `app:`/`user:` state учитывать общие области и конкурентные сессии, чтобы откат одного append не отменял успешное изменение другого. Сохранить штатную семантику ADK partial events, temporary keys и дедупликации.

Файл заменять атомарно только после получения корректного JSON; при неудачной записи исходный файл остаётся читаемым. Не сообщать UI, что событие надёжно сохранено, до завершения commit. Ошибка IO должна быть отдельной понятной ошибкой, не замалчиваться.

Проверить тот же контракт в `create_session()`/`replace_session()`. Существующий `web/checkpoints.py` использует `to_jsonable_python(..., fallback=str)`; унифицировать требования к исполняемому state, чтобы checkpoint не маскировал то, что не принимает основной storage. Представление для экспорта и данные для возобновления — разные контракты.

### 5.3. Уже затронутая сессия

Не выполнять автоматическую «починку» истории удалением событий. Перед восстановлением сохранить доступные snapshot, transcript и checkpoints; определить последнюю непротиворечивую точку.

После исправления кода перезапуск загрузит старый дисковый snapshot, но сам по себе не вернёт несохранённые ревизии. При доступном корректном checkpoint возможен явный resume из него. При отсутствии — пользователь выбирает повтор планирования с объяснением потери несохранённого прогресса. Нельзя повторно запустить уже выполненные внешние задачи без проверки их артефактов/идентификаторов.

Данный документ не меняет и не перезапускает эту сессию. При диагностическом импорте моделей штатная инициализация приложения сообщила о записи локального `.opik.config`; это побочный эффект импорта, а не часть предлагаемого исправления. В тестовом окружении такие bootstrap-эффекты следует изолировать.

## 6. Карточка согласования и восстановление

Переиспользовать `plan_to_view()` и существующую HITL-карточку. Добавить явные разделы: версия плана; почему остановлены доработки; что будет выполнено; оставшиеся замечания; непокрытые операции; технические блокеры; действия пользователя.

Основная кнопка — «Согласовать с замечаниями» только для разрешённого кандидата. При неисполняемом плане вместо неё — указание, что требуется исправить. Не помечать ожидание как «Выполнено» и не держать индикатор вычисления, когда ждём человека.

Идентичность review: `(session, run_id, kind, plan_id, revision, digest)`; transport UUID не заменяет её. Ответ связан с этой версией, повторная доставка или двойной клик не запускают задачи дважды. После изменения кандидата старое решение не применимо.

Reconnect браузера уже умеет повторно доставить in-memory request. После перезапуска процесса `_pending` и future исчезают: транскрипт сам по себе не возобновляет исполнение. Поэтому сохранить review record до публикации карточки; существующего observer-only checkpoint hook недостаточно как гарантии.

Для восстановления нужен детерминированный обработчик resume: загрузить pending record, перепривязать карточку, принять решение один раз, повторно проверить snapshot и продолжить с нужной стадии без LLM-перепланирования. Не пытаться сериализовать coroutine/future. Если автоматический resume пока не реализован, UI обязан явно показывать «нужно восстановить из контрольной точки», а не активную, но неработающую кнопку.

## 7. Порядок реализации и связь с кодом

| Этап | Файлы/узлы | Результат |
| --- | --- | --- |
| 1. Репродукция и безопасные errors | `experiments/critique/validator.py`, `experiments/review.py`, `experiments/context/builder.py` | Ошибочный план не ломает JSON; старые schema errors очищаются своевременно |
| 2. Защита storage | `web/durable_sessions.py`, затем `web/checkpoints.py` | Некорректное событие или ошибка записи не отравляют последующие запросы |
| 3. Кандидат и политика замечаний | `experiments/schemas/models.py`, `critique/validator.py`, `review.py`, `plan_view.py` | Текущий план сохраняется до одобрения; технические запреты отделены от согласуемых замечаний |
| 4. Исчерпание → human-review | `review.py`, `runtime/state_machine.py`, `hitl/models.py`, `hitl/handler.py`, `web/handler.py`, `hitl/mode.py` | Последняя версия согласуется человеком, включая auto; решение проверяется на сервере |
| 5. Единственный владелец approval | `assembly/assembler.py`, контракт конфигурации/`agents/experiments.yaml`, `experiments/prompts/templates.py` | Планировщик не создаёт лишние общие согласования до валидации |
| 6. Outcome, guards и UI | `runtime/coalesce.py`, `runtime/guards.py`, `context/builder.py`, граница ExperimentModule, `web/static/js/hitl.js`, `i18n.js` | Оркестратор понимает ожидание/блокировку; нет ложного reporting и повторных делегаций |
| 7. Durable review и resume | `web/handler.py`, `web/app.py`, checkpoint/session storage, UI восстановления | Переподключение, двойной ответ и рестарт не теряют согласование и не повторяют исполнение |

Этапы 1–2 можно выпускать отдельно: они не меняют поведение принятия научных решений. Этапы 3–6 составляют целостное изменение маршрута; не выпускать новый fallback с обходом auto/approval guards только наполовину. Этап 7 обязателен для обещания восстановления после рестарта.

Перед кодовыми правками повторно проверить существующий dirty worktree: `web/app.py`, `config/settings.py` и UI уже изменены другой работой. Не перезаписывать эти изменения. Изменения сериализации, review-flow и восстановления удобно разнести по отдельным коммитам.

## 8. Регрессионные проверки и приёмка

Тестировать на искусственных локальных данных без платных LLM, Docker-развёртываний и реальных экспериментов.

1. Ошибка зависимости `task_artifact/depends_on` и ошибка URL MCP дают JSON-native diagnostics; `json.dumps` и `Session.model_dump(mode="json")` проходят.
2. Невалидная версия → валидная схема с отклонённой критикой: старый `ValueError` и schema errors не остаются в актуальном state/feedback.
3. Полная цепочка review → event delta → AgentTool → durable append → reload → новое user-сообщение работает, а не только проверяет ключи mock-словаря.
4. Неизвестный объект в event/state отклоняется до commit; state, events и файл не меняются. Следующее корректное событие сохраняется.
5. Инъекция ошибки записи/`os.replace`: состояние не расходится с диском; откат не уничтожает успешные записи других сессий. Проверить stale ADK-копию, app/user scopes, partial и duplicate events.
6. Исчерпание бюджета с исполнимым кандидатом создаёт ровно одно финальное review. До ответа `start_task` невозможен. Не совершаются новые LLM-доработки.
7. Согласование запускает ровно показанный digest, оставляет исходный critique и сохраняет human decision. Непокрытые OP остаются видимыми в итоговом отчёте.
8. Reject, timeout и отсутствие UI не запускают эксперимент. Edit открывает новый раунд только по явному действию пользователя.
9. Невалидный текущий draft не затирает предыдущий валидный snapshot. Предыдущая версия не выбирается молча.
10. Невалидные зависимости, отсутствующий tool, disabled route, чужой run/digest и нарушение scope не обходятся approval.
11. Изменение inventory/settings между показом карточки и ответом проверяется повторно; если план изменён, требуется новое согласование.
12. Forced-human в `auto` действительно ждёт человека; обычный `auto` работает по-старому. Все транспорта сохраняют одну политику.
13. Проверка собранного agent tree: dedicated reviewer имеет внутренний handler, но не создаёт дублирующий generic approval. Другие агенты не теряют нужные HITL-возможности.
14. Пауза планирования возвращает конкретный outcome, не reporting-success; оркестратор не запускает повторный модуль и отчёт.
15. Refresh, reconnect, process restart, checkpoint restore, повторный ответ и поздний ответ на старую карточку не создают второй запуск.
16. Кандидат и решение не смешиваются между двумя одновременными сессиями. Новые state keys публикуются через AgentTool и очищаются только при действительно новом run.

Расширить существующие suites `test_review_state_publishing.py`, `test_plan_revision_budget.py`, `test_module_budget_and_pause.py`, `test_review_auto_approve.py`, `test_plan_view.py`, `test_web_hitl_sessions.py`, `test_hitl_a2a.py`, `test_hitl_agenttool_scope.py`; добавить самостоятельные storage round-trip/failure-injection тесты. Утверждения о timeout/pause в старых тестах обновлять осознанно под новый контракт, не просто удалять.

## 9. Наблюдаемость и границы работы

Во все review/persistence события добавить `session_id`, `invocation_id`, `experiment_run_id`, `plan_revision`, `review_id`, `reason_code`. Общий лог содержит параллельные сессии: близость по времени не доказывает общий run.

Отдельно считать отказы схемы, отказы качества, исчерпание бюджета, ожидание человека, timeout, ошибку сохранения и ошибку выполнения. Не отправлять весь план, входные данные или секреты в сообщение об ошибке сериализации.

Не включать в это исправление смену моделей, увеличение бюджетов, автоматическое развёртывание Docker/MCP или ослабление всех проверок. Цель — предсказуемый финальный выбор пользователя, устойчивое состояние и честный статус исследования.
